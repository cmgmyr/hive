# Worker state, and why it has an append-only log

Worker state (working/idle/waiting) comes from Claude Code hooks writing directly to the database, keyed by `HIVE_AGENT_ID`. hive depends here on a payload contract it does not own, cannot see change, and pins no version of.

## A state that corrects itself still has to be readable afterwards

`agents.agent_state` is one row overwritten in place, so a wrong value replaced a second later leaves nothing behind. Issue #24 was closed on that basis and reopened the same day: a false `idle` was written at 13:27:39 and overwritten with `working` at 13:27:41, the lead sampled at 13:28, saw `working`, and recorded a PASS on a lane that had already failed. No polling frequency anyone would really run catches two seconds.

So `agent_state_log` is append-only and the hook writes one row per invocation. Nothing updates a row and nothing deletes one except retention. Three things about it are load-bearing:

- **The `event` column.** Both #24 lanes reasoned from "an idle was written" to "`stateFor("stop")` wrote it" without checking, and the truth was that the notify branch wrote it. One column answers that at a glance.
- **The payload is stored raw and unredacted.** The bug turned on `notification_type`, a field nothing in hive read. A projection can only preserve fields someone already knew mattered, which is the same incomplete-corpus failure wearing a disguise.
- **The log write sits AFTER the state write, in its own try/catch, never sharing a transaction.** The state write is what wakes and `agent_status` depend on, so a log that cannot be written must cost the diagnosis, never the behaviour.

Assert over the SEQUENCE in this table, never over a sample of `agent_state`, or the test has the blind spot the table exists to remove. A sample is not evidence about a state machine; an event record is.

Retention is `pruneStateLog()` in `tick()` rather than in the janitor, because the janitor returns early when the tmux probe fails and a machine can sit that way for days.

## Enumerate every path that can write the value, before picking one

Two full lanes of #24 reasoned from an observed value to a presumed writer and neither checked. Three lines of `stateFor` return `idle` and only one was ever under investigation. The first fix was correct and fixed a door the bug was not coming through; it shipped with 50 green tests and the bug reproduced the same morning.

Any time you have "the system recorded X", the first question is which writer wrote it, not why the writer you have in mind would have.

## Five ways worker state has been wrong, and how each was closed

Same class each time: hive reported something it could not observe, or had the fact and did not say it plainly. The last two are the odd ones out and worth reading for the difference: there the state was **correct** and the meaning read off it was not. The fifth is the fourth arriving through the door the fourth's own fix did not cover.

- **#28** (closed 2026-08-08): a state that could not be written. A worker blocked on a permission prompt could not be reported, because `waiting` was latched with nothing to clear it. `noteBlockedWatched` (`src/scheduler.ts`) closed it: when a watched agent's state is `waiting` it reads that agent's pane directly and tells the wake's owner if a dialog is up, instead of waiting on a state hive cannot observe. Mechanism and edge cases in `.claude/rules/tmux-and-panes.md`.
- **#38** (closed 2026-08-02): filed as "a turn that dies mid-response leaves the worker on `working` forever and `wake_when_idle` never fires." That framing did not survive contact with the code: `max_wait_seconds` (900s default) already timed the wake out before this issue was filed, so it was never true that the wake waits forever. The real gap was narrower - `watchedTail` already embedded the agent's state and its pane tail in the wake body, but not the interpretation, so a lead reading "state now: working" next to a dead pane had to already know to distrust it. The fix folds that interpretation into the wake body directly. The paragraph below is that diagnostic; it stays true and worth knowing even with the fix shipped, since recognizing the shape on sight is still the fast path.
- **#46** (closed 2026-07-31): no canary over the payload contract, so a field changing shape would not have been noticed at all. `test/payload-canary.test.mjs`, plus its committed corpus, is that canary now.
- **#156** (closed 2026-08-11): a TRUE state read as the wrong event. `claude --resume` replays the restored conversation, ends that turn, and fires a Stop hook, so a resumed worker goes idle - genuinely, freshly, correctly - for a turn nobody asked for. A standing watch reported that as "finished" before the worker had been given its assignment, and a lead that trusts the wake tears down a worker that never started. **Nothing about the state was wrong**, which is why every guard already on this page missed it: `agent_state_log` records the transition faithfully, `idleIsAFreshTransition` is correctly true for it, and `resumeAgent`'s own latch reset (issue #154) cannot touch an idle that has not happened yet. Closed with `agents.resumed_at`, stamped by `resumeAgent` and cleared by `src/hook.ts` on the first `prompt` event, so `resumed_at != ''` read as "resumed, and not yet spoken to" (**todo 373 widened both halves - read that entry below before relying on either sentence**). **THREE surfaces answer "this worker is idle, act on it", and the fix had to reach all three** - `standingIdleRows` and `watchedStates` (`src/scheduler.ts`, the standing watch and the one-shot) and `wake_when_idle`'s own `mode="all"` already-satisfied shortcut (`src/tools/wakes.ts`), which returns before any scheduler code runs. The first version of this fix reached two of them and its own comment said "fixing only the half that was observed is how a defect ships twice"; it shipped three times, and counselors found the third. The predicate therefore lives in ONE module that names its readers - `src/stateProvenance.ts` when this shipped, `src/firstPrompt.ts` since todo 373 moved and widened it (below), where it is `awaitingFirstPrompt`. Reproduced before it was fixed, end to end and with no hand-written state: `test/resume-false-finish.test.mjs`.

  **SUPPRESSING A FINISH SILENTLY BREAKS THE DEATH REPORT, and that is the non-obvious half.** `standingGoneRows` excludes a closed row whose `agent_state` is `idle`, on the premise "idle means it had finished and this watch has ALREADY SAID SO". This suppression is precisely what falsifies that premise: the idle was deliberately not said. So a worker resumed at 09:00 whose restore turn ended and whose pane then died before any assignment landed was closed with the latch frozen at `idle`, and was silent in BOTH halves - no finish, no obituary, nothing in `hive status` - which is the worst outcome available, reached by two individually correct guards meeting. The gone query now reads `(agent_state != 'idle' OR resumed_at != '')`. **If you ever add a second reason to suppress a finish, this is the paragraph to re-read**: every finish-suppressing rule has to be checked against every rule that reads "already reported" off the same column.

  **A PARK IS NOT A DEATH EITHER.** `agent_park` (issue #156) closes the row deliberately, and a worker parked mid-work reads `working`, so without an exclusion every park filed an obituary telling the lead that worker died and to go and check its branch for what was lost - one per worker, at exactly the moment a lead parks a crew at the end of the day. `standingGoneRows` excludes `parked_at != ''` for the same reason it excludes a close from `idle`.

  **BOTH OF THOSE EXCLUSIONS READ COLUMNS ANOTHER WRITER CAN CLEAR, WHICH IS A THIRD DOOR INTO THE SAME FALSE OBITUARY (todo 374).** `resumeAgent`'s flip un-closes a row in one statement that also clears the park stamp AND resets `agent_state` to `unknown`, and its pre-pane failure path used to restore `status`/`closed_at` and nothing else. So a resume that died before its pane came up left a closed row with BOTH exclusions gone - `parked_at` cleared, `agent_state` no longer `idle` - plus a freshly stamped `closed_at`, which is the episode key every gone cursor and every `seedGoneCursor` row is written against. Nothing had ever recorded a cursor for the parked lane either, because the park exclusion is a FILTER rather than a claim. Every clause passed and the lead was told a lane it had parked the night before had died. Note the second half stands alone: an ORDINARY closed row that closed from `idle`, never parked at all, loses ITS exclusion by the same route. Closed by making the revert the flip's exact inverse rather than a list of the columns somebody noticed - see `RESUME_FLIP_COLUMNS` (`src/spawn.ts`), pinned by `test/resume-revert-restores-row.test.mjs`. **The transferable half: an exclusion is only as durable as the column it reads, so when you add one, ask who else writes that column and what their failure paths put back.**

  **The transferable half is the question to ask, not the column.** "Which writer wrote this value" (the section below) was the right question for #24 and answers nothing here, because the right writer wrote the right value. The question that finds this class is **"what did the worker DO to earn this state, and did anyone ask for it"** - and that is answerable from the same log, since a finish nobody asked for is an idle with no `prompt` before it.

  **It only ever suppresses, and that is what keeps it out of `also_when_stuck`'s grave** (`.claude/sessions/dead-ends/2026-07-29-also-when-stuck-on-latched-waiting.md`). That design FIRED on a latched state whose end emitted nothing. This one fires nothing, and the end of its condition emits a `prompt` hook hive already wires and already writes on. Read the dead-end's rule as it is written: a latch may decide whether to LOOK, never what is true. Deciding to STAY QUIET is the safe direction of the same rule.

  **The accepted residual, so nobody rediscovers it as a defect.** A delivery into a BUSY pane is absorbed into the running turn as an attachment and fires no `UserPromptSubmit` at all (`.claude/rules/tmux-and-panes.md`), so an assignment sent while the restore turn is still replaying leaves `resumed_at` set and that turn's real finish is suppressed too. Bounded, not permanent: the next delivery landing on an idle pane is a real user turn and clears the column. **Say what hive does and does not know here, because "no evidence of any kind exists" is too strong and was the recorded wording until todo 377.** hive's OWN delivery sites - `agent_send`'s text path and `deliver()` - are first-person evidence that something WAS given to this worker. What hive cannot tell is whether the in-flight turn's end includes that work: between a restore turn and an attachment-driven turn there is no `prompt` and no `working` latch to separate them. So the limit is on attributing the FINISH, not on knowing a delivery happened.

  **AND THE SILENCE IS NOW REPORTED, WHICH IS THE ONLY THING AVAILABLE (todo 377).** Every way the clearer fails to run produces one signature - a running `kind='agent'` row with `resumed_at` set, going on being suppressed - so `hive doctor` names such a worker past a **GUESSED** 30-minute bound (`reportUnbriefedWorkers`, `src/cli.ts`). Information, never a gate, on `reportPtyHeadroom`'s stance. It does not fix the absorbed delivery and must not be read as if it did; it converts "a lead waits forever" into "hive says which worker it has gone quiet about". Its headline claims only what hive OBSERVED - the latch has been set this long - never *why*, because the commonest route here is the absorbed delivery, where the worker was briefed and is working normally and only its FINISHES are lost.

  **THAT REPORT IS THE FIRST READER OF THIS COLUMN THAT DOES NOT SUPPRESS, AND IT FALSIFIED A RECORDED JUSTIFICATION (counselors, two seats).** `launchAgent`'s INSERT stamps `resumed_at` for every kind, and its own comment defended that on the grounds that an uninstrumented row "never suppresses anything either, because its `agent_state` stays `unknown` and every reader here is gated on `idle`". True of every reader that existed when it was written; todo 377 added one that REPORTS. `agent_spawn` sets `kind='agent'` for every command, so a bash or codex worker is a `kind='agent'` row whose latch can never clear - a non-claude pane fires no `UserPromptSubmit` - and it would have been named on every run for the life of the row, with a remedy that cannot work. Gated on `reportsAgentStateLog` (`src/stateProvenance.ts`), this project's own allowlist for "this row has a state channel". **The rule for the next reader of this column: if it SUPPRESSES, the `idle` gate covers you; if it REPORTS, ask whether the row has a state channel at all before you say anything about it.**

- **Todo 373** (closed 2026-08-12): #156's defect through the ordinary dispatch path. `agent_spawn` types a `[hive]` line into a brand-new worker's pane and SUBMITS it, so the worker answers it, that turn ends, Stop fires, and the row latches idle before anybody has given that worker a lane. #156 closed the resume end and left this one open, so the false finish fired on EVERY spawn made while a standing watch was up - which the runbook tells every lead to have. Watched four times in one evening. Reproduced end to end first: `test/spawn-false-finish.test.mjs`.

  **THE RESUME FIX DOES NOT TRANSFER, AND THE REASON IS THE WHOLE LANE.** #156 clears its latch on the worker's first `prompt` event, because a resume types NOTHING into the pane - so the first prompt really is the first moment somebody gave that worker something. A spawn speaks first, and **its announcement is a real `UserPromptSubmit`**. Measured on todo 373's own worker (`agent_state_log` for `agent:208`): `prompt|working` at 03:49:25 (hive's announcement), `stop|idle` at 03:49:30 (the false finish), `prompt|working` at 03:49:40 (the lead's actual assignment). A latch cleared on the first prompt is cleared five seconds before the idle it exists to suppress, and the fix ships green and does nothing. **If you extend this suppression to a third start path, ask what hive itself types into that pane before you reuse the clearing rule.**

  Closed by giving the clearing rule the one exception the announcement's own text already implies ("wait for your assignment"): `src/hook.ts` clears on the first `prompt` that is **not** hive's spawn announcement, discriminated by `isSpawnAnnouncement` on a constant `paneAnnouncement` itself is built from, so the two cannot drift. Matching hive's own text in a prompt payload is not new here - `checkConfirmations` recognises a delivered wake by its `[hive wake #N]` prefix the same way. A stamp written AFTER the announcement was typed was rejected: the hook fires in the worker's process while `sendText` is returning, so it is a race, and losing it reports the finish.

  **ONE COLUMN, NOT TWO, AND THE DECIDING READER IS A `WHERE` CLAUSE.** `agents.resumed_at` now means "started (spawned or resumed), and not yet given anything" - `launchAgent` stamps it in its INSERT, `resumeAgent` in its flip - and its NAME is half the truth, accepted rather than renamed. A second column would have to be OR'd in by every reader, and one of those readers is `standingGoneRows`'s SQL, which cannot call a JS predicate; widening one column means the finish-suppressing rule and the "already reported" rule above stay paired with **no edit to that query at all**. A `RENAME COLUMN` migration is append-only-legal and was rejected too: an MCP server started before it keeps running old `dist/` for the life of its session and would hit `no such column` inside the scheduler tick.

  **The predicate moved out of `src/stateProvenance.ts` to `src/firstPrompt.ts`, a leaf module with no imports**, and the move is forced rather than tidying: `src/dashboard.ts` is two of the readers (todo 366) and is deliberately free of any tmux dependency, while `stateProvenance.ts` imports `src/tmux.ts`.   **SUPPRESSING A FINISH IS NOT THE WHOLE JOB: SOMETHING ELSE THEN CLAIMS THE WORKER IS NOT THERE.** All three counselors seats overturned this lane's own recorded acceptance of one gap, independently, and the shape generalises past the instance. A standing watch's "Still going" roster filtered `agent_state != 'idle'`, so a suppressed worker dropped out of it - and an empty roster makes the notice say *"Nothing else in this project is running right now"*, an affirmative claim about the crew. The lane had recorded that as honest silence. It is not silence, and the minimum shape is the ordinary wave: A is assigned and finishes, B was spawned alongside it and not yet briefed, and A's notice denies B exists. **The pairing rule above, restated for this direction: every rule that SUPPRESSES has to be checked against every rule that says "and therefore nothing else is there".** The same audit found `hive status` and the SessionStart digest (`src/kickoff.ts`) printing "idle for 3m" for the same worker through `describeForHuman`; the digest is *injected into a fresh lead's context* next to the instruction to triage it, so a model consumes that sentence and proposes lanes off it. Both corrected, both pinned, and the exclusion that had kept `agent_status`/`agent_list` out ("they report the row rather than deciding on it") was WITHDRAWN in writing rather than routed around: the dashboard badges only report too, and this lane fixed them.

- **Todo 387** (closed 2026-08-13): **todo 373's own fix, above, is what makes this entry historical rather than current for the spawn side.** `agent_spawn` typing and submitting a `[hive]` line was the turn every paragraph above exists to manage - and todo 384 found the deeper cost: if a lead's real assignment landed while that self-inflicted turn was still running, it could be absorbed into it as an attachment with no `UserPromptSubmit` to clear the latch, and since the ordinary dispatch shape is brief once and wait, the suppression was **operationally permanent** for that worker - not the "bounded, not permanent" residual todo 373 recorded. An adversarial pass (agent:216) then found the announcement's own drain path was not the only one (`.claude/rules/tmux-and-panes.md`'s busy-pane section now says so), and proposed removing the turn rather than making its consequence recoverable: **nothing is typed into a spawned worker's pane anymore.** `SPAWN_ANNOUNCEMENT_PREFIX`, `isSpawnAnnouncement`, and `src/hook.ts`'s exception for the announcement's own prompt are all gone. `launchAgent`'s INSERT no longer stamps `resumed_at`; only `resumeAgent`'s flip does, so the column is back to meaning exactly what its name says - "resumed, and not yet given anything" - and every paragraph above about a SPAWNED worker's false finish describes a defect that structurally cannot recur, because there is no longer a turn for a busy-pane assignment to land inside. **What did not change**: resume's own restore turn is real Claude Code behaviour, not something hive types, so it is untouched, and everything above about the resume half stays current. `test/spawn-false-finish.test.mjs` now asserts the replacement invariant - a spawned worker has no turn at all until briefed - rather than the suppress-then-clear mechanism this entry describes.

**The reader list lives in that file and is authoritative there, not here** - a count restated in prose is a count that goes stale the next time somebody adds a reader, which is the same failure this entry is about. What is worth carrying: the readers span `src/scheduler.ts` (including one that is a SQL `WHERE` clause), `src/tools/wakes.ts` and `src/dashboard.ts`, plus the writer that clears the column, and **two of them are in one file** - which is why todo 366's own "the dashboard is a fourth reader" undercounted. Count the badge sites, not the files.

Spotting the pattern is still cheap: a worker whose last `agent_state_log` row is a `prompt|working` with no `stop` after it, whose pane shows an error and an empty input box, and whose branch has not moved. A `working` older than the lane's rhythm is suspicious; `working` is not self-evidently healthy. Recovery is to send it a message, and to tell it what state you found, because after an API error it does not reliably remember what it was doing.

## A debounce is not an inference

Both appeared in one lane and only one was legitimate. The notify branch asserted a fact it could not see: the input box has been quiet for sixty seconds, therefore the worker is finished. It was deleted for that. A dwell that waits for a state to stop changing and reports what it observed asserts nothing, is self-verifying, and can only make a wake late rather than early. If you write one, say in the code which kind it is, because the next reader cannot tell from the shape.

## Never set a /goal on a worker

A goal fires the Stop hook after every turn while immediately starting another, so hive records idle for a worker that never stopped. Nine consecutive false idles were measured on agent:53 in 50 seconds with no `prompt|working` between them. `agent_state_log` does not save you here: the rows are not corrupt, they are each briefly true and instantly stale. The lead has an agents row now (issue #27) and writes hook rows like any other actor, but stays safe because its hook writes no STATE row: `src/hook.ts`'s `agents.agent_state` UPDATE is scoped to `WHERE ... AND kind = 'agent'`, an allowlist rather than a lead-specific skip (so a future third kind defaults to the same silence, not to getting state written by accident), so this exact churn lands in `agent_state_log` only, where it is harmless and best-effort forensics rather than a false idle something else acts on.

## Wake-up bodies are delivered verbatim into a terminal

Whatever you pass as a wake body is typed into the target pane exactly as written, and it becomes a fresh user turn only if that pane happens to be idle. So write it as plain English that stands on its own: the ids it refers to, the context needed to act, and the next action.

The failure this prevents is a body that only parses as a reply. "Yes, go ahead with option 2" is unreadable when it lands mid-turn hours later next to work that has moved on, and there is no thread for the reader to scroll back to. Assume the reader has none of the conversation that produced the wake, because usually it does not.

**A delivery into a BUSY pane can never be confirmed, so `unconfirmed` does not mean undelivered.** The text is absorbed into the turn already running, no `UserPromptSubmit` fires, and `confirmed_at` can never be set for it. Do not read that as a failure and do not build anything that waits for a late confirmation. The mechanism, and the two paths where a wake genuinely never fires, are in `.claude/rules/tmux-and-panes.md`: a pane sitting on a dialog, and a pane holding unsubmitted human text. Both hold past `max_wait_at`, and the second was added deliberately - delivery pastes and presses Enter, so a box with text already in it would submit the wake merged with whatever the human was typing.
