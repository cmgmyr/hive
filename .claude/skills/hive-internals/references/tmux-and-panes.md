
# tmux, panes, and typing into them

These cost real state when they were broken: a live worker closed mid-lane, and a wake that answered a dialog nobody read. Each is enforced by code and pinned by a test. Do not remove a guard because its reasoning is not in `CLAUDE.md`; the reasoning is here and next to the code.

## A private tmux server paired with the DEFAULT store is refused, not believed

A probe against the wrong server SUCCEEDS and answers the wrong question correctly, so nothing in the snapshot separates it from a genuinely dead pane. `targetAlive("%3", snapshotOfSomeOtherServer)` is false for exactly the reason a dead pane is false.

`untrustedTmuxServer()` refuses the pair. `liveTargets()` and `targetLive()` answer `null`, which every consumer already handles conservatively. `launchAgent` refuses ABOVE its INSERT, because the row is the first statement precisely so a rejection never leaves a half-built pane. Both halves are gated, reads and writes: under the bad pair `sessionName()` returns the untagged name, `ensureSession` creates a second session on the private server, and the pane id from that fresh server gets written into the SHARED store, where it very likely names a stranger's pane.

Get the boundary right. The danger is a private socket plus the DEFAULT store, not isolation as such. Legitimate isolation sets BOTH a private `TMUX_TMPDIR` and a scratch `HIVE_DATA_DIR`, and the entire suite depends on that staying allowed.

**That sentence is about the STORE guard only, and a later fix made it false for the ATTACH path, so say which guard is which.** `untrustedTmuxServer()` refuses a PAIR (private socket + default store) and full isolation is deliberately exempt from it, exactly as above. `ensureAttached()` refuses on the SOCKET ALONE, and full isolation is refused by it - the very configuration the paragraph above calls legitimate. Both are correct because they answer different questions. The store guard asks "can this process's beliefs about panes be trusted", which the scratch store answers. The attach guard asks "can the window I am about to open reach the session I am about to name", and the store has no bearing on that at all: see "iTerm profile commands run with no shell" below for the mechanism, and `ensureAttached`'s own comment for the argued case list. The test is which socket tmux will actually use, computed in tmux's own order of precedence: `TMUX`'s first comma-separated field, else a reachable `TMUX_TMPDIR`, else `/tmp`, always `<base>/tmux-<uid>/default`. Three earlier versions asked a proxy question instead and each was wrong differently. Two corrections worth keeping: tmux does not create `TMUX_TMPDIR`, so a value naming a missing directory resolves to the SHARED socket; and inside a pane `TMUX` overrides `TMUX_TMPDIR` completely, so `tmux -L spike` is a private server with no `TMUX_TMPDIR` set at all.

Pinned by `test/server-store-mismatch.test.mjs`.

**The guard is now data-shaped, not just env-shaped.** Issue #73 added `agents.tmux_socket`, written in the same statement as every `tmux_target` write: `launchAgent`'s INSERT and its pane UPDATE (`src/spawn.ts`), and `ensureLeadRow`'s fresh INSERT and `cmdLead`'s restart CAS (`src/cli.ts`), all from `tmuxSocketPath()`, the identical function `untrustedTmuxServer()` above already decides server identity with. `foreignSocket()` plus the row-level `rowLive()`/`rowAlive()` (`src/tmux.ts`) refuse to believe a row whose recorded socket disagrees with the one this process would talk to: they answer `null`, the same conservative unknown every consumer here already had to handle for the process-level guard. An empty socket means "no fact recorded", never foreign - every row written before this migration reads that way and behaves exactly as it did before, so a second shell setting only `HIVE_DATA_DIR` no longer closes every worker in the spike store; it now gets `null` for each one instead and sweeps nothing. Wired into `isLive()`/`summaryLiveness()` (`src/tools/agents.ts`, the choke point for `agent_close`/`agent_send`/`agent_list`), the janitor's agents sweep and its timers sweep (a timer LEFT JOINs to its `deliver_actor`'s own agents row for this, since a timer names a pane, not a row, and a join miss reads as the same "no fact recorded" empty case, scoped to `agents.status = 'running'` - see `DELIVER_SOCKET_JOIN`'s own comment for why an unscoped join let a closed row launder a foreign pane past this guard), `deliverable()`, `watchedTail()`'s and `hive doctor`'s own per-worker pane-capture reads (two independent call sites, each gated separately rather than through one shared helper), `watchedStates()`'s idle-wake check, and `startYmlCommand`/`cmdLead`'s stillThere check/`hive doctor`'s lead report (`src/cli.ts`).

A review pass on PR #80 found this claim overclaimed its own coverage: `deliverable()`, `watchedStates()`, `startYmlCommand`, `cmdLead`'s stillThere check and doctor's lead report had no test at all. The fix that followed closed some of that gap and is honest about what remains. Pinned now: `test/tmux-socket.test.mjs` (the write side); `test/tmux-socket-foreign.test.mjs` for `isLive()`, both janitor sweeps, `tick()`'s `deliverable()` (a fixture with two lead rows sharing one `actor_id`, one closed on this socket and one running on a foreign one - the shape the join scoping above exists for), and `tmuxSocketPath()`'s own directory-only canonicalisation (`canonicalSocketPath()`, so an unlinked-then-recreated socket file cannot flip a live row foreign); `test/false-idle.test.mjs` for `watchedTail()`'s foreign-socket gate; and `test/state-provenance-cli.test.mjs` for doctor's per-worker pane-capture gate and its stuck-row report (a foreign-socket running row the janitor cannot sweep, named rather than left silent). Two of those four have since gained one: `watchedStates()`'s own foreign-socket branch (`test/standing-watch.test.mjs`'s "does not believe a running row whose pane it cannot see, or cannot see into") and `cmdLead`'s stillThere check (`test/lead-restart-gaps.test.mjs`'s "BEHAVIOUR 4"). `startYmlCommand` and doctor's lead-liveness report still have no test against a genuine foreign socket, as opposed to an unanswered probe; narrowed here rather than left to overclaim.

A later review pass found this list itself under-claiming in the one place it most needed to be right: `test/server-store-mismatch.test.mjs` pins `defaultTmuxSocketPath()` (which calls `canonicalSocketPath()` internally) against an independently-derived regex, not against a second call to the same function - the one assertion in the suite that actually kills a constant-returning `canonicalSocketPath`. The two dedicated tests in `test/tmux-socket-foreign.test.mjs` do not: they only assert the function agrees with itself across two inputs, which a hard-coded constant would also pass.

**A socket path is a location, not a server identity (accepted and recorded, not fixed).** `tmuxSocketPath()` keeps only the path field of `TMUX` (`<path>,<server pid>,<session>`) and drops the pid. Two different tmux servers that reuse the same socket path - the ordinary case across a reboot, since tmux always names the default socket `<base>/tmux-<uid>/default` - compare equal here. After a reboot, rows recorded on the old server are never foreign to the new one, pane ids restart at `%0` and collide with whatever the new server has already issued, and `agent_send` can type into the wrong pane. Pre-existing, not something this lane introduced, but this is the lane that claims to close the env-shaped residual above, so the claim has to stop short of "which server" and say only "which socket path". Closing it for real needs the pid or the socket file's inode recorded alongside the path - a second migration, not a fix that belongs in this one. See `tmuxSocketPath()`'s own comment (`src/tmux.ts`). **Narrowed since, not closed.** A migration recording a pid did land - `agents.pane_pid` (below) - and issue #157 (further below) makes it a third call site. It is a PANE's pid, not the SERVER's this paragraph asks for; see the next paragraph for exactly what it does and does not close.

**The `agents.pane_pid` migration closed the PANE half of this, not the SERVER half - say precisely which, because the two read as the same fix and are not.** `foreignSocket()`/`rowLive()`/`rowAlive()` above still compare only the socket path, exactly as this paragraph describes; nothing about them changed, and issue #149 below does not touch this either - the socket-identity residual stays open. What changed is narrower and sits one door over: `agents.pane_pid` (`#{pane_pid}`, written wherever `tmux_target` is - `src/spawn.ts`'s `launchAgent`, `src/cli.ts`'s `ensureLeadRow` and `cmdLead`'s restart CAS) is joined into `deliverable()` (`src/scheduler.ts`) as `deliver_pane_pid`, and a wake whose target reads live but whose current pid disagrees with the recorded one is held rather than delivered. A third call site landed later, in `cmdLead`'s own adopt check rather than a delivery - see issue #157 below. Measured, matching this paragraph's own numbers: `#{pane_start_time}` was empty in the tmux version checked (unusable), `#{pane_pid}` differed across a restart (50926 -> 50942) with the pane id identical (`%0` both times) - so pid answers "is this the pane we meant", which is a narrower and cheaper question than "is this the server we meant", the question a socket-identity fix would still have to answer for every other consumer of `rowLive`/`rowAlive` in this file. **PIDs wrap.** A reissued pane can in principle land on its predecessor's exact pid, and the check passes and delivers wrongly exactly as it does with no column at all - guardrail against a confused machine, matching this whole file's stance, not a guarantee and not a security boundary. `test/lead-pane-reissued.test.mjs` reproduces the real sequence (kill every session so a real tmux server exits, start a fresh one on the same socket, assert the wake does not land on whatever pane the fresh server's own first pane turns out to be) rather than asserting the condition against a synthetic snapshot, and now covers both a lead-owned and a worker-owned wake.

**Issue #149 widened the check above from lead-only to every `deliver_actor`, and corrects the reasoning that gated it in the first place.** The `agents.pane_pid` fix gated the check on `isLeadActorId` alone, on the stated grounds at the time that "worker rows are reaped by `janitor()`'s per-tick sweep before this class of staleness matters". **That was false for this specific condition, and the paragraph above already refutes it**: `deliverable()`'s dead-pane hold only fires when the recorded pane reads DEAD, `janitor()`'s two sweeps acted only on the identical `rowAlive(...) === false` condition, and a reissued pane reads LIVE - the sweep the gate leaned on was blind to precisely the case pane_pid was added to detect. So a worker's overnight wake could be typed into whatever pane inherited its id after a reboot, and since this protection is claude-chrome-shaped (below), a non-claude pane has none of it - the paste would execute. `deliverable()` now runs the pid comparison for every target; the reason string differs by target (`HELD_REASON_PANE_REISSUED_LEAD` names `hive lead` as the remedy, `HELD_REASON_PANE_REISSUED_WORKER` says plainly that nothing re-points a worker's wake the same way) because only a lead's wake has that rescue.

**Issue #157 added a THIRD call site, and it is the ADOPT decision itself, not a delivery.** The `agents.pane_pid` fix and issue #149 both close cases where hive is about to TYPE into a pane it already holds as this actor's own; neither touches the earlier question of whether `cmdLead` should take a pane back into that role in the first place. `cmdLead`'s adopt check used to ask only "is the pane live" and "is it in a window this project owns" - a bare shell `hive attach` leaves in a fresh session's initial pane passes both, so a reboot followed by `hive attach` then `hive lead` could adopt that shell, the restart CAS would record its pid, and every pending lead-owned wake would get re-pointed at it; the next delivery then pastes into bash and executes, precisely the CLAUDE-CHROME-SHAPED gap below describes for a non-claude pane. The adopt check now runs the identical `rowLiveProbe`/`paneReissued` comparison the two paragraphs above already use, so a pane whose recorded pid disagrees with tmux's own is refused rather than adopted. The found-window branch it falls through to on a refusal already existed, for the pre-existing stranded-pane case, and splits a fresh pane in beside whatever the stranger's pane is without killing it - not hive's pane to kill, and PIDs wrap makes killing it on this comparison alone the wrong kind of confident. `test/lead-restart-gaps.test.mjs`'s BEHAVIOUR 5/6 pin the mismatch-refuses and empty-pid-still-adopts cases the same way the earlier pid fix's own control pair does.

**Hold, not cancel, for a non-lead mismatch too - argued explicitly because the lead case's safety net does not extend to a worker.** `hive lead` re-points every pending lead-owned wake to its fresh pane in the same transaction that records it (issue #27, `cmdLead` in `src/cli.ts`; issue #157 above is what makes *fresh* pid-checked rather than merely assumed, since the adopt decision that pane came from used to be pid-blind - and PIDs still wrap, so a matching pid means "not provably a different process", never "provably the same one"); nothing does the equivalent for a worker's wake, so a held worker wake has no automatic rescue. **A plain `wake_set` (`kind='delay'`, the commonest wake by far) never gets a `max_wait_at` at all** - only `wake_when_idle` writes that column - so say precisely what a held worker wake waits on: a human (or a running lead) noticing it and cancelling it, or nothing, ever. An earlier version of this paragraph named `max_wait_at` as a third escape alongside those two; that was false for exactly the wake kind this whole argument is about, caught in review and corrected here rather than left standing. Chosen anyway, because a cancel is silent (the wake is simply gone) while a hold stays visible: `wake_list` is scoped to `project_id`, not to `owner` or `deliver_actor`, so any session in the project - not only the wake's own owner - sees a held worker wake's `held_at`/`held_reason`, and `hive status`'s `heldWakes` count is the same project-wide, no-owner-filter query. "Visible in `wake_list`, and bumps a count `hive status` already prints" is the honest answer to where a human would see it; it is not "nowhere", but it is also not automatic the way a lead's re-point is - a human has to be looking.

**Three findings from that review pass, all closed in `src/scheduler.ts` and `src/tools/wakes.ts`.**

- **A hold used to be only a one-tick promise.** The pane a worker's wake was reissued to is its own process, and nothing stops it from exiting too - a transient shell, often within minutes. When that happened, the janitor's timers sweep and `deliverable()`'s own dead-pane branch both saw `rowAlive(...) === false` and cancelled the timer outright, exactly as they always had for an ordinary dead pane - silently reaching the outcome the hold-over-cancel argument above exists to avoid, through the other door. `held_reason` is now the durable signal that tells the two conditions apart (`wasHeldForPaneReissue`): a timer already held for a reissue that later goes fully dead stays held, with an updated reason naming both facts, rather than being cancelled with no trace. The updated reason is built from the SAME shared prefix the original reissue reasons use, deliberately - proven the hard way, by mutation: a reason that does not itself satisfy `wasHeldForPaneReissue` gets re-evaluated and re-cancelled by `deliverable()` on the very same tick the janitor sweep just held it, since a held-not-cancelled timer is still due and still an active candidate.
- **The worker-facing held reason used to name a remedy the reader could not reach.** `wake_cancel` was owner-scoped only (`WHERE owner = ?`), and a plain `wake_set` with no `deliver_to` makes the worker both owner and `deliver_actor` - once the janitor closes that worker's row (the very next bullet), no session can ever call `currentActor()` and get that `actor_id` back, since identity comes from the caller's own environment and nobody may assume another actor's on its behalf. `wake_cancel` now lets a running lead (`isRunningLeadActor`, the same row-verified check `agent_close`'s lead-target refusal uses) cancel any pending wake in the project, not only its own - matching the reasoning that made "hold" safe in the first place: a lead is who `wake_list` and `heldWakes` are visible to, so a lead is who needs the power to act on what it can already see. Ownership is still the only route for anyone who is not a running lead.
- **The `pane_pid = ''` "no fact recorded" case was pinned for `deliverable()` but not for the janitor's widened agents sweep.** The existing test seeded a `kind='lead'` row, which that sweep filters out entirely (`kind != LEAD_KIND`), so the branch this lane added never saw it. `paneReissued`'s own `recordedPid !== ""` guard was already correct; what was missing was a worker-owned test that actually reaches the widened branch, so a future removal of that guard - which would read every worker row recorded before the pid column existed, with its live non-empty pid, as a manufactured "mismatch" against its empty recorded one, and close all of them on the first post-upgrade tick - would be caught rather than shipped green.

**The agents janitor sweep was widened to match; the timers janitor sweep was deliberately NOT, except for the already-held-for-reissue exemption above (a timer held for a reissue that later goes fully dead stays held rather than being cancelled).** `janitor()`'s agents sweep (`src/scheduler.ts`) now reaps a reissued row the same way it already reaped a dead one, through the same `paneReissued()` predicate `deliverable()` uses, so a reissued worker row no longer keeps reporting "running" to `agent_list`, letting `agent_send`'s `requireLive` type into a stranger's pane, or letting `watchedTail` capture-pane a stranger's screen into a wake body - all three were still poisoned even once delivery alone was held. The timers sweep's dead-pane cancellation otherwise stays unwidened for the reissued case on the identical reasoning as before: cancelling a reissued timer outright would reach past `deliverable()`'s own hold decision by a different route, before the wake is even due and before a human ever sees it held. See that sweep's own comment in `src/scheduler.ts`.

**Issue #27, and how issue #73 closed it.** A lead row used to be immortal (the janitor exempts `kind='lead'`, `agent_close` refused it outright), so `hive restore` could only ever GUESS at a lead's liveness before deciding whether the store was in use - and each of two earlier attempts at a guess failed a different way. The fix stopped guessing: `hive restore` now counts any running lead row as in-use unconditionally, with no probe at all, and `agent_close` gained the retirement path that makes that safe - it closes a lead whose pane is CONFIRMED dead. "Confirmed dead" means `isLive()`, and until issue #73 that resolved through the same cross-server blind spot: a caller on the wrong tmux server calling `agent_close` on a lead whose real pane lives elsewhere got a false "dead" (`targetLive` answered `false`, not `null`, because the wrong server genuinely has no such pane) and retired a row that was actually still running. `isLive()` now consults `rowLive()` first, so that same caller gets `null` and `agent_close`'s own `if (live === null) throw probeFailed(agent)` - already sitting above the confirmed-dead close - declines instead of retiring. Pinned by `test/agent-close-foreign-socket.test.mjs`, alongside the control that the matching-socket case still retires exactly as before.

**Issue #27's own residual text overclaimed here, and a later fix is the correction, not a widening.** That residual text wrote "closing this one deliberately (a human choosing to run `agent_close` on a specific, named lead)" as if that were already true. It was not: nothing checked who the caller was, so any WORKER could call `agent_close(name: "lead")` exactly like a human at a terminal, including hitting the cross-server false-dead case above against a lead it has no business touching at all. `agent_close` now refuses outright - before probing liveness, so this applies whether the target reads live, dead, or unprobed - whenever `currentActor()` starts with `agent:`. A plain claude session is `user:<name>` and a peer lead is `lead:N` (`src/context.ts`), so a human at a terminal and a peer lead both keep the retirement path; only a spawned worker loses it. For those callers, the cross-server false-dead case is now closed too, by the paragraph above: this is a caller-KIND gate for who may reach the retirement path at all, alongside a liveness-TRUTH fix for what that path believes once reached.

## A row's `tmux_target` is always a PANE id, whatever the placement

From a live incident. `placeAgentPane` (`src/spawn.ts`) used to return the WINDOW id for `placement="window"`, so those rows read `hive-main:@3`. A pane belongs to exactly one window permanently and `join-pane`/`break-pane` MOVE it (`decisions/2026-08-05-tmux-topology-windows-not-sessions.md`), so joining such a worker's pane into another window destroys the window its row names. `janitor()`'s agents sweep then gets an honest `false` from `rowAliveProbe` - not the `null` the foreign-socket conservatism protects - and closes a row whose `claude` is still mid-turn. **A WORKING WORKER READS AS FINISHED**, the standing watch reports it finished, `agent_send` stops resolving it, and nothing repoints a worker's `tmux_target` afterwards. Reproduced locally end to end, asserting the process alive through the kernel and not through hive's own view of it: `test/window-target-moved-pane.test.mjs`. That topology decision had already named this exact consequence six days before it happened, in its own last paragraph.

**Nothing downstream had to change to keep working, and the reason is a measurement rather than an argument.** Against tmux 3.7b, in both directions: `rename-window`, `kill-window`, `show-options -w` and `split-window` all accept a `%pane` and resolve UP to its window; `capture-pane`, `send-keys` and `display-message` all accept an `@window` and resolve DOWN to its ACTIVE pane. So the column's two kinds of id were never a compile-time-shaped problem. What differed was only which pane the pane-scoped readers MEANT - and there the window id was the defect: a window-placed worker's window can hold a second pane, because `splitTargetWindow` puts a split-placed CHILD into its parent's window, so `agent_output`/`agent_status`/`watchedTail` could return the child's screen and `agent_send`/wake delivery could type into it. Narrower than it reads (`split-window -d` leaves the parent active, so it needs the active pane to have moved) and closed as a side effect rather than reproduced end to end. Said that way deliberately: the tmux resolution half is measured, the end-to-end half is not.

**Two sites read `isPaneTarget(tmux_target)` as a stand-in for PLACEMENT, which is not stored anywhere.** That conflation was the root cause, not the sweep. `agent_rename` now asks the window its own name (`ownsItsWindow`, above), and `killAgentPane` (`src/tools/agents.ts`) now reaches `kill-pane` for these rows where it reached `kill-window`. **That is a BEHAVIOUR CHANGE riding inside a "store a different id" patch, which is the shape this project keeps shipping by accident, so it is named here as well as in the code**: identical for the ordinary sole-pane window (tmux reaps a window whose last pane dies), and different in exactly one case - closing a window-placed worker no longer takes down a split child sharing its window. **`killAgentPane`'s window branch is NOT dead code and must stay**: an MCP server started before this change keeps writing window ids into the shared store for the life of its session (`common-issues/stale-mcp-server-runs-old-code.md`), and `kill-pane` against a window id fails, so deleting it would leak a live process instead of erroring.

**The defect is reachable by following hive's OWN advice, not only by an ad-hoc lead action**: `hive doctor`'s duplicate-window-stamp report tells a human to "Move the panes into one window (tmux join-pane -t <window>)". That is the incident's operation, printed by hive.

**NO `placement` COLUMN, argued rather than skipped.** `agent_resume` already re-derives placement from `hive.yml` and the environment rather than reading it off the row, so this codebase already treats placement as a per-spawn input and not a durable property; a column would be a second source of truth for a fact the code deliberately does not keep, made permanent by append-only migrations, for one cosmetic consumer. The argument is at `placeAgentPane` in the code, not only here.

**The pane-reissue guard (the `agents.pane_pid` fix / issue #149) STOPS BEING INERT for these rows, and that was a decision.** `targetLiveProbe` returns `pid` null for a window target, so every `placement="window"` row carried `pane_pid=''` - "no fact recorded" - and `paneReissued` could never fire for one. They carry a real pid now. Kept rather than suppressed, because the move this defect is about cannot trip it: measured, a pane keeps both its id and its `#{pane_pid}` across `join-pane`. What it can now catch for these rows is what it was built to catch. **The reachable consequence is worth knowing before you write a test**: `respawn-pane` gives a pane a new pid, so repainting a worker's screen that way now reads as a hijack and reaps the row. Four existing fixtures did exactly that and had been resting on this exemption without knowing it; `repaintPaneAsSameWorker` (`test/helpers.mjs`) is the repair, and it explains itself. It repairs until the row STICKS rather than writing once, because the sweep can read a row before that write and close it after - `closeAgentRow`'s CAS carries no pid, so a corrected pid does not stop it.

## A pane must never be recorded onto a row that is no longer running

Issue #156, found in review by every reviewer independently. `recordPane` (`src/spawn.ts`) is the
last write of both `launchAgent` and `resumeAgent`, and it used to be
unconditional (`WHERE id = ?`). Both callers span real tmux forks between
deciding the row is theirs and this write, so the row can be retired
underneath them, and the result is a live `claude` process recorded against a
row that says closed. That row is invisible to `janitor()`'s agents sweep
(`status = 'running'`), so nothing ever reaps it.

**How it was reached, because the shape is worth recognising rather than the
instance.** `resumeAgent`'s flip deliberately commits `status='running'` with
`tmux_target=''` to take the row out of the janitor's `tmux_target != ''`
window. A concurrent `agent_park` reading that row gets `{live: false}` from
`targetLiveProbe('')` - **FALSE, not `null`** - so the caller's own "unknown
liveness is never dead" refusal does not fire, it kills nothing, and
`parkAgentRow`'s CAS compares `''` against `''` **and matches**. The row goes
closed+parked mid-resume. Two guards that are each correct in isolation, and
the empty string that makes one of them work is what defeats the other.

It is not a narrow window: `placeAgentPane` runs inside `withWindowClaim`
(`BEGIN IMMEDIATE`), so a competing write BLOCKS on that lock and fires the
instant it releases - straight into the gap. Contention makes it MORE likely.

`recordPane` now takes `AND status = 'running'` and returns whether it wrote.
**The caller owns the recovery**, because only the caller knows what it built:
`changes === 0` means there is a live pane belonging to nobody, so both callers
kill that pane and throw. Leaving it is the one outcome that leaks a process
nothing tracks.

Fixed at `recordPane` rather than at the caller that exposed it, deliberately:
`launchAgent` has the identical INSERT-to-`recordPane` gap (an `agent_close`
landing in it), so a guard written into the park path would have left that twin
live while reading as a fix. **The invariant is one sentence that does not
mention park at all** - a pane must never be recorded onto a row that is no
longer running - which is what makes this the right layer for it.

Pinned by `test/recordpane-row-retired.test.mjs`, which asserts the ROW *and*
the PANE. Asserting only that the call throws would pass against both versions,
since the pre-fix code throws nothing at all.

**One consequence for anyone patching this SQL in a test.**
`test/spawn-cwd-scope.test.mjs`'s "finding 5" intercepted this statement with
`===` against a full literal, and adding the `WHERE` clause silently stopped
that match, turning a real regression test into one that proved nothing. It
matches with `startsWith` now. A test that intercepts SQL by exact string is a
test that disarms itself the next time anyone touches the query.

## tmux session names are namespaced by data store, not by project

One session per STORE, one window per project inside it: `sessionName()` takes no argument and returns `hive-main` for the default store. Project ids are SQLite row ids, unique only within one store, so a project id was never a safe namespace on its own, and tmux session names share one machine-wide namespace regardless. `sessionName()` tags the name when `HIVE_DATA_DIR` is not the default; the default store keeps the documented `hive-main`.

Naming goes through the same guard as opening: `dataDirTag()` is `tagFor(storeDir())`. It was exempt for one commit on the grounds that building a string touches no disk, which answered the wrong question, since a session name is the target argument for `kill-session` and `respawn-pane`. A scratch store still needs its own namespace for the identical reason it always did: `hive-main` in a scratch store must not resolve to the live session of the default store's own project window.

## Aliveness checks use `list-panes`

`display-message -t` silently falls back to a default target when the given one is dead.

## Hive-owned windows carry hive's required tmux options

Every window hive creates is marked with the window option `@hive-owned=1`
and receives `allow-passthrough all`, `pane-border-status top`, hive's pane
border format, and `monitor-bell on` before its real process starts. A split
may target a window the user created, so an unmarked window is the user's and
hive must not write these options to it. The settings are best-effort: losing
cosmetic configuration must never fail a spawn whose process is already live.

## A project's window is found by its `@hive-project-id` stamp, never by name

Under one store-scoped session (`sessionName()`, above), every project's
window carries `@hive-project-id`, set in the same `configureHiveWindow` call
that sets `@hive-owned`. `cmdLead` (`src/cli.ts`) resolves a project's window
by reading this stamp off the session's windows, never by matching the
window's name. `splitTargetWindow` (`src/spawn.ts`) reads it too, but only as
the fallback for a spawn with no resolvable parent - a split worker's
PRIMARY placement is the store lookup one section below (`parent_actor_id` ->
the spawning lead's `agents` row -> `tmux_target` -> its window), never the
stamp and never ambient `TMUX_PANE`. A window name is cosmetic now (the
project name alone, not "<project> - lead"), and two projects can
legitimately share one: only `path` is unique in the `projects` table, so two
real checkouts named the same thing is not a hypothetical.
Reading `@hive-project-id` at window scope needs no `-A`: measured live
against a real tmux, `show-options -w` (with or without `-A`) and
`list-windows -F` all agree once a value is set at window scope, whether
queried via the window itself or via one of its panes. `-A` only matters
descending FROM window scope INTO a pane-scope `show-options` query - a trap
hit once before with `allow-passthrough` (a genuinely pane-inherited option) -
never at matching scope, which is what every `@hive-project-id` read is.

A worker's own placement="window" (its own dedicated window, not a split into
its project's) does not stamp ownership yet - a known gap, outside what this
invariant covers and not closed anywhere else in this file.
**The "and still resolves by `windowTitle()`" half of this
sentence was misleading and the row's-`tmux_target` fix above made it
load-bearing, so say what is actually true of that title now.** Nothing ever
RESOLVED a window by title -
`windowTitle()` has only ever been used to NAME one, at the two sites that
create one (`placeAgentPane` and `resumeAgent`, `src/spawn.ts`). What is new
is that the title is now also READ: `ownsItsWindow` (`src/spawn.ts`) decides
whether `agent_rename` may retitle a window by comparing that window's current
name against `windowTitle(project, the row's current name)`. So the naming
convention has become a fact hive depends on rather than decoration, and a
change to `windowTitle`'s format silently stops window retitling rather than
merely relabelling tabs. Every miss falls through to "do not retitle", pinned
by `test/agent-names.test.mjs`.

`allow-passthrough` is a pane option inherited from the window. Probes must
use `show-options -p -A`; without `-A`, tmux reports that inherited, working
value as unset.

## A split worker's window is the SPAWNING LEAD's window, resolved from the store

`splitTargetWindow` (`src/spawn.ts`) resolves a split-placed worker's target
window through `parent_actor_id` -> the parent's `agents` row -> its
`tmux_target` (a pane id - true of EVERY row since the fix above, see "a row's
tmux_target is always a pane id" above, where it used to hold only when the
parent happened to be split-placed) -> `paneWindow()` of that pane - never
through ambient `TMUX_PANE`, which names whoever happens to be calling rather than
who the row says spawned this worker, and never through a window name
(`decisions/2026-08-05-tmux-topology-windows-not-sessions.md`). This is
the cross-repo case the whole redesign started from: a worker's STORE scope
(`agents.project_id`) and where its PANE appears are separate questions, and
a worker recorded under a different project than its spawning lead is meant
to land in the lead's window regardless (`.claude/rules/project-scoping.md`
now names this as a third axis, beyond files and store).

The parent row's `tmux_target` is trusted only after `rowLive()` returns
`true` - the same foreign-socket conservatism every other tmux_target read
in this file already applies. A parent row recorded on a socket this process
cannot see into must read as unresolvable, not as "no parent"; skipping this
check would let a stale or foreign parent row send a worker's pane to a
window on a server this process has no business trusting. When the parent
is unresolvable (no row, dead pane, foreign socket), `splitTargetWindow`
falls back to `findProjectWindow` (the `@hive-project-id` stamp lookup,
above) - the honest answer for a spawn with no resolvable parent: an
unattended run, or a caller that is not a lead.

## Never type into a pane that is waiting on a choice

Delivery is a paste followed by Enter. A pane showing a modal has nowhere to put the paste and reads the Enter as "choose the highlighted option", so the wake vanishes, no user turn is created, and hive answers a prompt nobody read.

A pane that is merely BUSY is fine, and that conclusion still holds. The mechanism this file described until 2026-08-02 did not, and the difference decides how you read a wake that never confirms.

Measured against Claude Code 2.1.220 by delivering a wake into a worker that was mid-turn: the paste is enqueued (a `queue-operation` transcript entry with `operation: "enqueue"`). From there **there are two drain paths, not one** - corrected here after a later measurement against 2.1.231 found the discriminator between them.

Path A: the entry is removed from the queue and enters the RUNNING turn as `type: "attachment"` carrying `attachment.type: "queued_command"`. No `UserPromptSubmit` fires. The original measured wake took this path: read and acted on 3.1s after typing, while the turn it interrupted carried on to its own end. So NOT delivered as a user turn, and NOT held until the turn ends - both still true, but only of this path.

Path B: the entry is DEQUEUED once the running turn ends, arrives as a genuine user message, and `UserPromptSubmit` fires normally - an ordinary user turn in every way that matters downstream. Observed on a second worker, same Claude Code version and machine as a path-A sample, 13 minutes apart.

**The discriminator is whether a tool boundary falls after the enqueue.** If the target still has a tool call pending, the queue drains INTO the running turn at the next tool boundary - itself another inference step, so the model necessarily sees the injected text before the turn can end (path A). If the enqueue lands after the last tool call, the turn ends first and the queue drains as a fresh turn (path B). It is a RACE decided by timing relative to the target's own tool calls, not a rule hive controls. Treating path A as the only outcome is what made a bounded residual read as permanent, and it is equally what makes path B's silent success invisible to a reader who only knows path A exists.

The consequence below is path A's alone; path B confirms exactly like any ordinary user turn and needs no special handling. An attachment (path A) fires no `UserPromptSubmit`, so no `prompt` row reaches `agent_state_log`, and `checkConfirmations()` in `src/scheduler.ts` can only set `confirmed_at` from a prompt row carrying the `[hive wake #N]` marker at or after `typed_at`. A wake delivered into a busy pane and drawing path A arrives, is read, is acted on, and still reads `unconfirmed` for the rest of its life. That is a PERMANENT false negative on that draw, not a delivery that confirms late. `timers.typed_busy` (schema v8) records the busy observation at typing time so the two cases can be told apart afterwards.

**Measured again against Claude Code 2.1.237 (2026-08-20):** 42 deliveries into a busy pane, spread across a single long tool call, medium-cadence multi-step turns, and 20 wakes at roughly one-second spacing over a 20-step turn, drew path A all 42 times - zero path B. This is a BOUNDED NEGATIVE, not a disproof of path B: `wake_set`'s `delay_seconds` is integer-only (`src/tools/wakes.ts:234`), so the finest landing granularity the tool can produce is one second, and the race described above plausibly resolves at sub-second timing this method cannot reach. Nobody has evidence for why the 2.1.231 and 2.1.237 results disagree - a real behavior change, a timing shift that narrowed the race below one second, and a difference in how the two measurements were run are all still open. Read both measurements as dated observations of a moving target, not as a settled mechanism.

Busy is still not modal, and conflating them still sends you fixing the wrong thing.

How this stayed wrong is the transferable part. The old sentence claimed it was "verified twice against the transcript on disk", and the wake text genuinely IS in the transcript, so a reader who goes looking finds it and reads an attachment as a user turn. The transcript answers "did the text arrive". It never answers "did a user turn begin". For the second question read `agent_state_log`. A record citing one channel cannot settle a claim about the other, and both of this project's records about this made that mistake in opposite directions.

The same measurement names a confirmation channel hive does not use yet: the transcript entry is structured JSON, carries the `[hive wake #N]` marker in `attachment.prompt`, is timestamped, and sits at a path hive already resolves for claude workers (`resolveTranscriptDir` in `src/transcript.ts`, reached today only by `agent_status`'s `transcript_dir` in `src/tools/agents.ts`). That is a better instrument than scraping a rendered pane, and it is still coupled to undocumented Claude Code internals, so weigh both before building on it.

Five paths type into a pane, guarded two different ways. This said "four" until a later count found them all: `agent_send`'s `keys` path reaches `tmux send-keys` directly rather than through `sendText`, so a grep for `sendText` callers finds four and misses it.

Three of the five can reach the LEAD's pane, and that bound is worth knowing before you go looking for which path clobbered a human: the scheduler's delivery, `agent_send`'s `text`, and `agent_send`'s `keys` (which is refused only for a non-lead CALLER, so a peer lead still reaches it - `keys` does not press Enter on its own, so it corrupts the box rather than submitting it). The other two cannot. `agent_rename` throws on a `kind='lead'` target before it reaches any typing. The spawn announcement is stronger than "does not target a lead": every branch of `launchAgent` returns a pane from `split-window` or `createWindow` and there is no respawn-into-an-existing-pane branch anywhere, so its target is a pane created microseconds earlier running a freshly launched claude - **structurally incapable** of holding anyone's unsubmitted text. That is why it is exempt from the input check below while `agent_rename` is not.

- `deliverable()` in `src/scheduler.ts` **HOLDS**. A wake is a timer that retries, so a dialog delays it: not cancelled, not claimed. The check sits ABOVE `claimOneShot`, because after the claim "not now" and "never" are the same thing.
  **Issue #28, THE HALF THAT MATTERS MOST: a wake_when_idle whose watched worker is stopped on a dialog never reaches this hold at all.** `maybeFireIdle` gates on `ready` before it consults `deliverable()`, and `ready` means a watched agent went IDLE. A worker on a dialog is `waiting`, never idle, so that wake never becomes due, is never held, and its owner hears nothing until `max_wait_seconds` - fifteen minutes on the default. `noteBlockedWatched` (`src/scheduler.ts`) closes that: when a watched agent's `agent_state` is `waiting` it reads that agent's pane, and if a dialog is up it tells the wake's owner. **The latch never decides anything; it decides only whether it is worth LOOKING.** That is the whole difference from the withdrawn `also_when_stuck`, which fired on `waiting` itself and died because a stale `waiting` and a live one are byte-identical in the store: here a stale one produces a pane read with no dialog on it and nothing is sent, so the store is never asked the question it cannot answer. No wake fires on `waiting` - the original wake's firing condition is untouched. The once-per-condition key cannot ride on `held_at`/`held_reason` here (the wake is neither due nor held, and writing them would make `hive status` report a delivery hive never attempted), so it is the `wake_block_notices` table, keyed on the agent's own `state_changed_at` so that blocked → answered → blocked again re-arms by construction. Both halves claim through that same table, which is what stops one block being reported twice when a wake can reach both paths in one tick.

**THERE ARE THREE READERS OF THAT KEY NOW, NOT TWO.** The stall detector's arm 2 (`noteStalledCrew`, `src/scheduler.ts`) reads the identical population - a crew member latched `waiting` - and reports the opposite conclusion about it: that the pane shows NO dialog and the worker's transcript has gone quiet, i.e. its turn appears to have died. Without a shared key the two would claim in different tables, and a dialog answered between one instance's pane read and another's produces two paragraphs about one worker that contradict each other on the one fact that decides what to do next. So arm 2 calls `claimBlockNotice` FIRST, on the same `(timer_id, agent_id, blocked_since)` triple, and files nothing if it loses - `wake_block_notices.blocked_since` and arm 2's episode are the same value, so one key covers one `waiting` episode whichever condition reaches it first. **If you add a fourth reader of a `waiting` worker, join this claim rather than inventing a key.** The accepted residual is recorded at `claimStallBatch`: this table has no `notice_timer_id`, so arm 2's own delivery-failure re-arm is defeated by the block key it already consumed. Cost discipline is part of the design: the `waiting` prefilter is a column read filtered in SQL, an already-notified block skips the pane read entirely, and the fork itself goes through the tick's `ChoiceCache`.

  **What that closes for a ONE-SHOT wake it did NOT close for a STANDING watch, until a later fix.** `blockedWatchedAgents` read its membership from `JSON.parse(timer.watch)` and answered `[]` for an empty list, and a standing watch (`wake_when_idle(scope: "project")`) stores `watch='[]'` because its MEMBERSHIP IS A QUERY over the project rather than a list - a consequence of the design, not a protection anyone chose. (An earlier version of this paragraph said the empty list was "load-bearing for mixed-version safety". That is false, and `src/db.ts`'s `watch_scope` migration says so in terms: what stops an old scheduler firing such a row early is `maybeFireIdle`'s `states.length > 0` guard, which predates all of this. The false reason travelled from the original bug report into the lane plan and from there into the code and this file; check `db.ts` before restating it.) So this half was STRUCTURALLY DEAD for the shape this project now tells leads to prefer: the finish half cannot see a blocked worker either (it is `waiting`, never idle), and the owner heard nothing until the watch expired, four hours later by default. Membership is now the watch's own - the same project/`kind='agent'`/`status='running'` predicate the finish half uses, with `agent_state = 'waiting'` where that one reads `'idle'`, sharing one column list (`CREW_COLUMNS`). They are NOT one row set: each excludes the actor it would otherwise be telling about itself, and this half resolves that actor owner-first while the finish half uses `deliver_actor`, so the two diverge whenever a watch's owner and its delivery target differ. Two things differ from the one-shot half and each is deliberate. The standing half is **BATCHED**: every crew member found blocked in one tick is claimed inside one transaction and named in ONE notice, because a notice is a paste into a terminal and project scope removed the bound an explicit watch list gave the notice count; the one-shot half stays per-agent, since its count is bounded by what the caller asked for. It carries its **own body**, because every clause of the one-shot's sentence is false for a watch that never fires and whose `max_wait_at` is a lifetime rather than a deadline it races.

  **The pane read is now bounded ACROSS ticks for BOTH halves, which is not a difference between them.** A pane found to have NO dialog is not re-read for 30 seconds - an in-process, negative-only, time-bounded observation, sitting in the shared loop, so the one-shot half inherits it too (`src/scheduler.ts`'s own comment argues why that is not the unbounded per-episode negative issue #28 rejected, why it lives in memory rather than in the store, and why the TTL rather than the socket check is what bounds a stale answer). The price is stated where the bound is claimed: a real dialog is reported up to 30 seconds late, against a baseline of not being reported at all, and on the one-shot path that is a change from "the first tick that saw it".

  **Who a block notice is filed at, corrected in the same lane.** It goes to the wake's OWNER, falling back to the wake's own resolved delivery target when that owner has no running `agents` row - which `resolveDelivery` (`src/tools/wakes.ts`) deliberately supports, so a plain `user:` session used to be told nothing at all. It is the reverse of the standing watch's FINISH notices, which go to `deliver_pane` first: a finish notice is the wake's own payload, so it belongs at the target the caller named, while a block notice is a meta-notice ABOUT the wake, so its reader is whoever is waiting on it. **Read plainly, that means a standing watch's block notice OVERRIDES `deliver_to`** - a deliberate exception to the promise `wake_when_idle`'s receipt makes about where a watch speaks, taken because the alternative is silence in the case below. The owner is preferred only while its pane is confirmed LIVE: a lead's row is exempt from the janitor, so a dead lead pane stays `running` indefinitely, and preferring it over a live `deliver_to` would claim the block episode and tell nobody. **The cascade does not reach these notices**: a block notice carries no `parent_timer_id` - whether it should is still open - so `wake_cancel` does not cancel one and `NOTICE_MAX_AGE` does not bound its age. Switching the block half to `deliver_pane` wholesale was measured and rejected - a wake delivered TO the blocked worker would file its only notice at the dialogged pane, where the self-report skip drops it, restoring the silence.

  **The MODAL hold also TELLS the wake's owner, at most once per hold condition, and does it without adding a typing path.** A lead sets a wake, goes quiet because the runbook tells it to, and used to be told nothing at all while the worker it is waiting on sat on a dialog. `noteModalHold` (`src/scheduler.ts`) claims the TRANSITION into `HELD_REASON_MODAL_CHOICE` with the same atomic conditional UPDATE shape `claimOneShot` uses - required rather than preferred, since one scheduler instance runs per session and an in-process guard cannot see the others - and inserts a due-now timer aimed at the owner's pane. The next tick delivers that through this same `deliverable()` check, so a notification aimed at a pane that is ITSELF on a dialog, or holding unsubmitted human text, holds exactly like any other wake instead of typing into it. The recursion guard is structural rather than a flag: a notification is inserted with `owner === deliver_actor`, and a wake whose owner is also its delivery target has nobody to tell, so a held notification never files another one. (A pane comparison alone was the first version and is weaker - the stored pane is frozen while the owner's pane is re-resolved, so a lead restart could make them disagree; it is kept as a second check for two actors whose rows name one pane.) On the blocked-watched path a chain is impossible for a different structural reason, and the fix above changed which fact carries it. It used to be "a notification carries the default empty watch list" - but an empty watch list is exactly what stopped meaning "watches nothing" once an empty list on a `watch_scope='project'` row means "ask the project". What holds now is that `insertNotice` sets NEITHER column, and `src/db.ts` declares `watch` NOT NULL DEFAULT `'[]'` with `watch_scope` nullable and no default, so a notice carries `watch_scope IS NULL`, stays a one-shot, and its empty list means what it always did. `kind = 'delay'` keeping it out of `maybeFireIdle` entirely is the second, independent reason. The ORIGINAL wake is untouched - not fired, not cancelled, not rescheduled - which is what keeps this out of the withdrawn `also_when_stuck` design (`.claude/sessions/dead-ends/2026-07-29-also-when-stuck-on-latched-waiting.md`). Pinned by `test/wake-hold-notify.test.mjs`, whose headline test was proven red against a version that notifies per tick.

- `agent_spawn`'s announcement, `agent_rename`'s `/rename`, and `agent_send`'s `text` path **REFUSE**. Each has a synchronous caller standing right there, so they return a receipt naming the dialog and carrying the pane's tail.
- `agent_send`'s `keys` path is **DELIBERATELY UNGUARDED against a dialog** and must stay so. `text` means "inject a user turn", which is what a dialog eats; `keys` means "drive this TUI on purpose", and pressing a key is the ONLY supported way to unstick a pane sitting on a dialog. Guarding it by symmetry would remove the one working escape hatch.

  **Issue #27: this path gained a SEPARATE guard, against a different target, not a reversal of the paragraph above.** The dialog exemption is an argument about a SUPERVISOR unsticking a SUBORDINATE's TUI, and it does not reach the lead: nothing supervises the lead, the same premise `agent_close`'s own refusal rests on. Without a kind check, a worker could send `keys: ["C-c", "C-c"]` (or `C-d`) at "lead" and end its session exactly as effectively as the `agent_close` this project already refuses, with no dialog guard, no `confirm_self`, and no kind check of its own to catch it. `agent_send` refuses `keys` on a `kind='lead'` target when the CALLER is not itself a lead; `text` on a lead is unaffected, and a lead sending `keys` to another lead is unaffected, preserving the escape hatch for the multi-lead direction this project is deliberately building toward. Pinned by `test/typing-guards.test.mjs` alongside the dialog cases above.

  **Issue #27, from review: "the caller is itself a lead" is checked against a real, running `kind='lead'` agents row (`isRunningLeadActor`, `src/spawn.ts`), not against `HIVE_AGENT_ID` alone.** `isLeadActorId` is a string prefix check with no row lookup behind it, so a caller could satisfy it by setting `HIVE_AGENT_ID` to any string shaped like `lead:<n>`, naming no row at all - the branch's own test proved it, passing `HIVE_AGENT_ID: "lead:999"` with no seeded row and getting the escape hatch anyway.

  **This refusal is a guardrail against a confused model, not a security boundary, and that distinction matters for how you reason about it.** It is not equivalent to `agent_close`'s refusal, which is enforced regardless of what tools the caller reaches for. A worker with Bash reaches the exact same outcome as raw `keys` by calling `tmux send-keys` directly, since that runs outside hive entirely; and `agent_send`'s own `text` path is untouched by design (see above), so `text: "/exit"` ends the lead's session with no `keys` involved at all. Do not extend this into refusing slash commands on the `text` path to close that gap - that is scope creep on an already-deep lane, and the residual is written down here instead. Worth recording alongside it: the WAKE route is genuinely closed, and for a real reason - `deliver()` prefixes every body (`src/scheduler.ts`), so a wake body can never be a bare slash command.

The discriminator is `paneChoiceCheck()` / `paneAwaitingChoice()`. A dialog is the footer AND the absence of the input-box marker, never the footer alone: matching the footer alone was tried and broke, because a worker that greps for the string, or opens a captured fixture, renders it in its own transcript and gets refused forever with no real dialog to clear. A modal REPLACES claude's input affordance rather than sitting beside it, so the missing input box is the real signal. One predicate is shared by the readiness probe, this discriminator, and `input_box` reporting, and the three do not want the same correction: the readiness probe and this discriminator are both hurt by OVER-matching (a false-ready spawn types into an unrendered pane and loses the text; a false input-box-present here is the `╰` bug itself, described below), while `input_box` reporting is hurt by UNDER-matching (`classifyInputBox`'s own gate returns null - "nothing to report" - the instant the predicate fails, so a real pending human-typed box it misses reads as absent and a wake can clobber it unheld). That is what the old "so do not widen it" was protecting.

**A LATER FIX REPLACED THAT PREDICATE, AND EVERY `INPUT_BOX_PRESENT` BELOW THIS LINE IS HISTORY.** The regex `/for shortcuts|shift\+tab to cycle|mode on|permissions on/` is gone; `inputBoxOnScreen` (`src/tmux.ts`) answers the same question by finding the BOX. The three-way asymmetry above is unchanged and is still the thing any future correction has to satisfy - what changed is what "the input box is on screen" is evidence of. Read the paragraphs that follow as the record of what the footer-matching version got wrong; their conclusions are not retracted, they are the argument the replacement had to answer. The section "the footer slot is not a marker, it is a slot" below states what the anchor is and what it costs.

**An earlier fix corrected this sentence rather than obeying it, and the correction has to be argued here, not just made in the diff (`covering-rules.mjs` names this file as covering that lane).** The blanket "do not widen" silently assumed the existing three alternatives already covered every healthy screen, so any widening could only ever be adding slack. That is not "narrower than ideal", it is a total miss, and a total miss on this shared regex is not the safe failure this file's own framing implies: every manual-mode `agent_spawn` returned `ready:false` with a false "may lose typed text" warning, and - the sharper cost - `isAwaitingChoiceScreen` for a manual-mode pane reduces to `CHOICE_DIALOG` alone, since `!INPUT_BOX_PRESENT` was permanently true with nothing left to ever make it false. That reopens the EXACT bug this file already documents two paragraphs up ("a worker that greps for the string... gets refused forever with no real dialog to clear") for the entire manual-mode population, permanently - worse than any plausible cost of widening, and the engagement the old sentence's "do not" owed but never made.

It does not change the direction argued above: the three consumers still fail in opposite directions exactly as this paragraph describes, and this is a narrow correction to a gap in COVERAGE, not a loosening of the boundary the old sentence was defending. Not a regression (`(shift+tab to cycle)` still covered it at normal widths, so nothing shipped broken), but the identical total-miss shape this whole section argues is serious, left open for the one mode this project's own maintainer runs by default. Measured at 220/80/60/40/30/25 columns: "bypass permissions on" survives everywhere `(shift+tab to cycle)` does not, intact through 30 columns and gone by 25 (cut down to "bypass" alone). `permissions on` added rather than the fuller phrase - measured to break at the identical width, so the shorter fragment costs nothing. `test/fixtures/panes/bypass-mode-idle-narrow.txt`, captured at 40 columns deliberately (every other fixture here is 220) so the fixture actually isolates the new alternative rather than also carrying `(shift+tab to cycle)` intact.

**The residual, stated rather than left implicit - CLOSED BY THE BOX-ANCHOR FIX, and the way it was closed is not the way this paragraph predicted.** `INPUT_BOX_PRESENT` was an unanchored match over the whole capture (see "boxed tool output sitting above a genuine dialog" below, and that paragraph's own correction: `paneAwaitingChoice`'s consumer, not `inputBoxState`'s, is the one actually bounded to 18), so `mode on` or `permissions on` appearing in a worker's own transcript - discussing this exact lane, or a captured fixture, the same way `Esc to cancel` already can - read as input-box-present above a real dialog and suppressed detecting it. That is the `╰` bug's shape with a different string, and it was not new: `for shortcuts` and `shift+tab to cycle` carried it from the start, for the identical reason.

This paragraph then rejected anchoring, and the rejection was sound about the thing it examined and wrong about the thing it concluded. What it examined: anchoring the MATCH to the pane's own last non-blank line. That does hold for `mode on`/`permissions on` and not for `ctrl+g to edit in`, which sits several lines above its dialog's trailing help line (`test/fixtures/panes/plan-approval-dialog.txt`), so a single anchor DEPTH across a set of unrelated substrings really is not cheap or safe. What it concluded, and what the box-anchor fix refuted: that the only way forward was a per-alternative anchor depth, i.e. a restructuring of `paneChoiceCheck`. The alternatives were never the thing worth anchoring. **Anchor on the BOX and the question of where each substring sits stops existing.**

## The footer slot is not a marker, it is a slot

From a live measurement on main rather than a hardening idea. Every alternative in `INPUT_BOX_PRESENT` was a substring of the permission-mode footer; claude draws that footer on ONE line and uses the same line for other transient hints. ## The window belongs to the HALF, not to the caller

This is the residual directly above, fixed by moving neither of the two things that residual named as the candidates. Both candidates - widening `tailCaptureLines()`, or handing `paneAwaitingChoice` the raw window whole - change the window for BOTH halves of `CHOICE_DIALOG && !inputBoxOnScreen` at once, and those halves fail in OPPOSITE directions. This file had already said so in words ("`CHOICE_DIALOG` stays the loose half of the pair on purpose"; "`INPUT_BOX_PRESENT` is what carries the precision") and the code then handed both halves one screen. **The defect was never that the window was too small. It was that one window was answering two questions.**

So the halves take two windows out of ONE capture. The footer half keeps the narrow trim-then-slice window unchanged - it is hurt by OVER-matching, and its false direction is a permanent unclearable dialog on a pane with no box to falsify it, so a wider window is strictly worse for it. The box half takes the raw window `inputBoxState` has always read - it is the FALSIFIER, hurt by UNDER-matching, and its false direction deletes the falsifier and degenerates the pair. `paneAwaitingChoice` and `paneChoiceCheck` read the box over the raw window. **The other two box readers deliberately do NOT, and getting that wrong was this lane's own follow-up finding.** The first version moved `paneHasInputBox` and `waitForPaneInput` onto the raw window too, on the grounds that "which window does the box search read" should have one answer - which is the same mistake one level down, because **the window belongs to the direction a reader fails in, and box readers split by that too.** RAW, because a MISS destroys them: `inputBoxState` (a missed box lets a wake paste over a human's unsubmitted message) and the falsifier half above. NARROW, because being FOOLED destroys them: `paneHasInputBox`, which `scripts/restart-lead.sh` refusal 1 uses as proof a pane is claude with `tmux kill-pane` on the other side of it, and `waitForPaneInput`, which types as soon as it says yes. There is deliberately no single answer, and the footnote is load-bearing rather than untidy. `captureRawPane`/`tailWindow` (`src/tmux.ts`) are that split, exposed rather than settled at the capture: `capturePane` is still `tailWindow(captureRawPane(...))` and every other caller is untouched.

**It costs no extra tmux work, and that is not a detail.** `capture-pane -S -18` already returns the visible pane PLUS 18 rows and `capturePane` threw the surplus away - measured live at three pane heights (69, 49 and 39 rows for `-S -18` against panes 50, 30 and 20 rows tall). Widening `tailCaptureLines()` would have, in every consumer of that constant at once: `inputBoxState`'s already-raw window, `watchedTail`'s wake-body capture, and `paneChoiceCheck`'s receipt tail.

**The blast radius is bounded by `BOX_MAX_ROWS`, which is why this is not "a bigger window with better manners".** `findInputBox` anchors BOTTOM-UP: the closing border must sit within `BOX_TAIL_ROWS` of the last non-blank row, and that row is the SAME row in both windows (`capturePane` strips trailing blanks before slicing; `findInputBox` strips them again itself). The upward scan is then capped at `BOX_MAX_ROWS`. So the raw window changes exactly one thing - whether a top border above the narrow window's own top edge is reachable - and it cannot admit a box from scrollback, because the bottom bound carries that and the bottom bound does not move. Checked against the fixture that would show it if that were wrong: `scrollback-box-above-dialog.txt`'s `╰` is rejected by `BOX_BORDER` rather than by the window, so it still reads `true`. Found in a later review pass; the code comment carried the same wrong citation and is corrected with it.) And the mutation that reverts the box half turns nothing else in `test/pane-fixtures.test.mjs` red either - the split is inert for the whole existing corpus.

**What it sells, in the fail-OPEN direction, which is the dangerous one, with both the arithmetic and the population corrected in a follow-up pass.** A screen carrying a COMPLETE box chrome - top border, `❯`+NBSP prompt row, closing border within `BOX_TAIL_ROWS` of the bottom - spanning that band can now suppress dialog detection where the truncated window could not see its top border. **The band is not 15-24, which is what this paragraph and the code comment both said.** That is the figure for a box with exactly 3 rows below its closing border; the general form is `(17 - (end - bottom)) + 1` up to `BOX_MAX_ROWS`, and `end - bottom` runs to `BOX_TAIL_ROWS` (8), so the floor is **10**. `footer-slot-taken.txt` carries 4 rows below its border and already sits at 14. ## A pane with unsubmitted human text holds its wake too

The sibling of the dialog hold, not a reversal of it, and the two are told apart by opposite signals. A modal REPLACES the input box, so `paneAwaitingChoice` needs the box ABSENT. A human mid-typing has a box very much PRESENT with real text in it, so the dialog check cannot see this case at all.

It matters for the same reason: delivery is a paste followed by Enter, so a box that already holds typed text gets the wake body pasted onto the end of it and both submitted as one message. Observed on two machines before this was closed - the wake arrives merged with whatever the human was halfway through writing.

`deliverable()` holds, above `claimOneShot`, exactly where the dialog check sits and for the identical reason: after the claim, "not now" and "never" are the same thing. The discriminator is `inputBoxState()`, which already existed and was reporting-only - its sole consumer was `agent_status`/`agent_output`'s `input_box` field. Only `pending` (real, human-typed text) holds. `ghost` must not, or every idle pane holds every wake forever, since an idle claude shows its own hint. `unknown` must not either: it means the detector's chrome-matching drifted (issue #30's shape), and a hold that silently starts firing on every unrecognised screen is worse than a detector that silently stops - the loud failure is `input_box` reporting `unknown` on a receipt, not a wake that quietly never fires.

**`agent_send`'s text path and `agent_rename` REFUSE on the same condition.** The scheduler was the sole consumer of this signal for a full release; both of these guarded a dialog and nothing else, so a worker sending text at the lead mid-sentence merged with it by construction, no bug required. They refuse rather than hold for the reason every synchronous path here refuses: a caller is standing right there to read the receipt.

`agent_rename` was found by a `/simplify` altitude pass rather than by the capture, and it is the worse of the two. It cannot reach the lead, which is what made it look exempt - but it types into a live WORKER pane, and the `lessons` pad's "unsubmitted pane text has happened three times" is about worker panes specifically. A slash command only executes at the start of a line, so `/rename foo` pasted onto a half-typed sentence submits the human's unfinished text with the command glued to the end of it, the retitle silently does not happen, and the receipt used to return `retitled: true` anyway. The receipt lied about the one thing it exists to report.

**The policy lives in `holdsHumanInput` (`src/tmux.ts`), next to `InputBoxState`, not at the three call sites.** Only `pending`, never `ghost`/`empty`/`unknown`/null. Review found the first two sites had already written `?.state === "pending"` twice by hand, which is exactly the drift `CHOICE_DIALOG`'s own comment prevents for the sibling signal ("One function so `paneAwaitingChoice` and `paneChoiceCheck` cannot drift onto two different definitions of dialog"). It takes an already-read box rather than a target, so it adds no capture and does not touch the no-fuse decision above: performing the read and deciding the policy are separate jobs, and only the policy is shared.

**The `unknown` exemption is fail-safe in DIRECTION and silent in PRACTICE, and both halves have to be said.** The direction is right, and it is why widening has to be argued here rather than at a call site: `classifyInputBox`'s dangerous failure is reading real text as a ghost, and that makes all three callers MISS, i.e. behave as they did before any of them existed. But the loudness this file used to claim - "the loud failure is `input_box` reporting `unknown` on a receipt" - **does not exist on the paths that clobber**, which review found independently, more than once. A successful `agent_send` with no `wait_ms` returns no `input_box`; a delivered wake reports nothing; `agent_rename`'s success carries no box. `input_box` appears on `agent_status`/`agent_output`, which nobody polls while sends look fine, and on the refusals that would have stopped happening. So a claude release that changes the prompt glyph while `INPUT_BOX_PRESENT` still matches reverts all three guards at once and says nothing, and no test can catch it either, because `test/input-box.test.mjs` replays frozen captures that still carry the old glyph. That is an argument for building the missing channel, not for widening the predicate. A later fix built it: `hive doctor` reads `inputBoxState()` for every running, non-foreign-socket claude worker in the current project and warns, by name, on any pane that classifies `unknown` - a second, deliberately unfused capture-pane fork per worker, non-gating (`--strict` does not fail on it), reporting three states unconditionally (classified cleanly, classified `unknown`, not classified at all) so a healthy run cannot be mistaken for a check that never ran.

**Say precisely what this closes, because a broader claim shipped here once and was wrong.** The first version reported only clean-vs-checked, and a `null` read silently counted as "classified cleanly" - review found this independently, more than once, on this lane's own PR, and the dangerous case is the one that matters: a TOTAL drift, where `INPUT_BOX_PRESENT` itself stops matching, makes every worker read `null` and the old counter reported "N of N classified cleanly" during the exact failure this check exists to catch. Fixed by counting three states instead of inferring one from a difference.

That fix draws the boundary this check has always actually had, though the first-shipped wording did not say so: **it closes the PARTIAL-drift case** - a box is genuinely on screen and the prompt row inside it cannot be found, `classifyInputBox`'s own documented failure shape.

**THE TOTAL CASE THIS SECTION LEFT OPEN IS WHAT HAPPENED, AND THE BOX-ANCHOR FIX CLOSED THE PRODUCER.** This paragraph used to end: a TOTAL drift - `INPUT_BOX_PRESENT` itself no longer matching - reads as `null`, is reported as "not classified", and is exactly as silent to the three callers as before the doctor-drift check existed. Every word of that was true, and it was not the distant chrome-redesign the phrasing implies. All four of that regex's alternatives were substrings of the permission-mode footer, all four lived on ONE line of claude's UI, and claude multiplexes that line with other transient hints. ## A tmux call that never answers is `null`, and it is a THIRD outcome

From the second crew-wide tmux loss in one day. `execFileSync` with no `timeout` blocks for as long as the child runs, which against a wedged server is forever: four tmux processes were found pegged at ~99% CPU, the oldest for 1h34m. Every call now carries a bound and `killSignal: "SIGKILL"`, since a wedged tmux is the process least likely to act on a SIGTERM.

**The bound is 10s and it is MEASURED, not felt.** Every command shape this file issues, timed against tmux 3.7b on a loaded private server (20 windows x 2 panes, each full of wide fully-attributed output), 60 iterations each: max 120ms idle, 155ms under 8-way fork contention, 103ms during a full `npm test`. The slowest SHAPE is a cold-server `new-session`, which forks the server itself. 10s is ~65x the worst observation. The headroom is wide on purpose - a legitimate call cut short answers `null`, so a healthy machine starts looking unknowable - and it is safe to be this tight because no call reaching `tmux()` is interactive: the one tmux call that blocks by design, `attach`, is spawned with inherited stdio from `src/cli.ts` and never comes through here.

**One shape is bounded by the USER'S CONFIG rather than by tmux, and this file used to say otherwise.** Starting a cold server SOURCES `~/.tmux.conf`, and `run-shell`/`if-shell` without `-b` block that startup, so a tpm line installing plugins on first run makes `ensureSession`'s `new-session` as slow as that config is - on `hive lead`'s own path, where the first run after a reboot would then be told "the tmux server may be wedged" on a healthy machine. Recoverable and loud, so it is a correction rather than a second bound. The measurements above are not from a bare machine: the box they were taken on carries a 6.3k `~/.tmux.conf` with an unbackgrounded `run` and an `if-shell`, and a cold-server `new-session` through it re-measured at 62ms. CI cannot see this at all - runners have no `~/.tmux.conf`.

**What a timeout MEANS is the half that decides whether this is a fix or the same failure through another door.** `tmux()` used to have two outcomes: an answer, or a `TmuxError` that `tmuxSaysNothingThere()` classifies. A timeout is a third, and reading it as the second reaps live workers, which is the exact failure the bound exists to prevent. `TmuxTimeoutError` is a SUBCLASS of `TmuxError`, so every existing catch site keeps working, and `tmuxSaysNothingThere()` refuses it BY TYPE above the stderr match rather than by string. It carries the dying child's PARTIAL stderr rather than `""` deliberately: with `""` the type check would be unfalsifiable decoration, since `NOTHING_THERE` cannot match an empty string anyway. `test/tmux-timeout.test.mjs` pins it with the matching-text case and proves it red three ways - the guard removed, the `ETIMEDOUT` branch removed, and the `timeout` option removed.

**`HIVE_TMUX_TIMEOUT_MS` is testing only** (a 10s bound can only expire in real time), read at call time, and `hive doctor` reports it when set, because a knob that shortens a safety bound must not sit in an environment silently.

**IT BOUNDS THE DAMAGE AND LEAVES THE CAUSE OPEN.** `execFileSync`'s timeout kills the CHILD, not the tmux SERVER it was talking to, so a wedge now costs ten seconds per call instead of an hour of a core, and the wedged server keeps running. Nothing here explains what wedges a server; that is separate, unsolved work. `hive doctor` counts the survivors (`orphanScratchServers`, `src/tmux.ts`): enumerated by SOCKET with the live socket resolved and excluded, aged by `stat` before anything is probed, probed through `tmux()` so the report cannot hang on the very condition it reports, and bounded by a total time budget it names when it stops. It REPORTS and never reaps - reaping has two recorded failures behind it, `dead-ends/2026-08-07-killing-orphaned-tmux-servers-by-pid.md` and `dead-ends/2026-08-11-reaping-a-wedged-tmux-server-by-socket-alone.md`, and a WEDGED server is counted separately precisely because the safe socket-only reap does not work on one. Two thresholds, both judgements rather than measurements and both argued in the code: a 1h age floor (20x the measured 181s full-suite run) so a concurrent suite's own sockets are not debris, and warn only for a wedged server or five-plus answering ones, since aged answering orphans are the everyday state of a machine that runs this suite.

## Two shell traps

- A leading `=` in a tmux target breaks when the string passes through zsh (path expansion). Safe in `execFileSync` arg arrays, unsafe in shell command strings. Target a session by id when its name starts with `=`.
- **Never run `tmux kill-server`.** It takes down whatever server the ambient env points at, which during development is the session the lead and workers are running in. Tear down with `kill-session -t =<name>`. This rule alone failed twice in one hour on 2026-08-14 (`dead-ends/2026-08-14-kill-server-as-a-tidy-up-step.md`), so a later fix enforces it in code for this repo: a `PreToolUse` hook wired from `.claude/settings.json`, running `scripts/tmux-kill-guard.mjs`, denies the bare form on the Bash tool before it runs. Know its limit before leaning on it: it guards the Bash TOOL, not the machine, so it does not see a kill inside a shell script file or a node `child_process` call.

## All process execution goes through `execFileSync` with argument arrays

`tmux()` in `src/tmux.ts` is the only way `src/` reaches tmux, and it takes an array. Never build a shell command string out of data. Pane titles, session names, agent names, wake bodies and `hive.yml` values all reach these calls, and every one of them is attacker-adjacent in the weak sense that matters here: they are typed by a human or written by a repo, not validated by hive.

An argument array has no shell, so quoting is not a thing you can get wrong. A command string reintroduces the whole class, and the shell trap above is the mild version of it that has already been hit: a leading `=` expanding as a path.

**That sentence used to say "this codebase" and it was FALSE in both directions, which the tmux-timeout fix made load-bearing rather than pedantic.** Six reads in `src/cli.ts` (`hive doctor`'s session, client, window and option probes; `hive restore`'s session check) reached `execFileSync("tmux", ...)` directly, and so did `quietTmux()`'s `has-session` on `hive lead`'s own path - so a fix applied at `tmux()` alone would have left the command a human runs BECAUSE tmux is misbehaving among the easiest places in the codebase to hang forever. All of them route through `tmux()` now, and the claim is scoped to `src/` because THE SUITE HAS ALWAYS REACHED TMUX DIRECTLY: ~190 raw calls across 37 files, of which the same fix bounded the two every file inherits (`isolateTmux`'s `cleanup()` and the shared assertion helper, `test/helpers.mjs`). The one raw call left in `src/` is `tmux -V`, which the client answers itself and never sends to a server.

## iTerm profile commands run with no shell and a minimal PATH

Auto-attach drives iTerm through AppleScript, and the command an iTerm profile runs does NOT get a login shell. It inherits a minimal `PATH` that does not include `~/.local/bin`, Homebrew, or any nvm or Herd directory, so a bare `hive` or `tmux` in one of those strings resolves to nothing and the failure surfaces as a window that opens and immediately dies.

Embed absolute binary paths in AppleScript strings. Resolve them at call time from the same place the dispatcher does rather than hardcoding a literal, since the interpreter this project pins moves with the machine's Node install (`.claude/rules/native-addon.md`).

**hive cannot ensure the window it opens reaches ITS socket, so a process on a private one must not open one at all.** `attachScripts` emits neither `-L` nor `-S`, so the tmux the AppleScript shell runs resolves its socket from that shell's own environment - and that shell is spawned by iTerm or Terminal, not forked from hive, so it inherits none of ours. `TMUX_TMPDIR` is not "lost in transit"; it could never have crossed. What lands on a private socket is therefore not an attach: it is a stray bare-shell session on the DEVELOPER's own tmux server, named for hive's store and grouped against a target that does not exist there, plus a control-mode client. Reproduced four times against a real desktop, then confirmed with a two-armed run differing only in `HIVE_AUTO_ATTACH`.

**Say it as hive's ignorance, not as tmux's behaviour, because the stronger claim is false and review broke it every time it was tried.** An earlier version of this paragraph said the window "can only ever reach the DEFAULT socket". It cannot be promised: Terminal's `do script` runs through the user's LOGIN SHELL (the "no shell does not mean no quoting" paragraph below says so itself), so `export TMUX_TMPDIR=...` in `~/.zprofile`, or `launchctl setenv` for the iTerm branch, hands that shell hive's own private socket by a route hive never sees. **What that costs, recorded so a later reader sees it was known rather than missed:** a user with such an rc, on a private socket, had a WORKING auto-attach and now gets a silent refusal. Still the right default - hive cannot read another process's rc, and being wrong in the permissive direction is the leak itself - but the refusal is justified by what hive cannot know, not by what tmux cannot do.

**The client is the damaging half, which is what decides the shape of the fix.** Killing the stray session does not make its control-mode client exit - it makes the client SWITCH to whatever session the developer is really using, and iTerm then mirrors their real windows as new native ones (measured while cleaning up after the confirming run). So the obvious cleanup action promotes the stray onto a live session. Any fix here has to stop the CLIENT being created; propagating `TMUX_TMPDIR` through the AppleScript string only re-points it, and adds quoting surface to a path with two recorded dead-ends about exactly that. `ensureAttached` (`src/tmux.ts`) refuses on `privateTmuxSocket()` instead, above the `list-clients` probe. The refusal is SOCKET-shaped and never mentions `HIVE_DATA_DIR`, deliberately: a scratch store on the DEFAULT socket is the only known way to exercise this function at all (`.claude/sessions/dead-ends/2026-08-02-ensureattached-against-the-live-session.md`), so a store-shaped refusal would have deleted its own test method. What it costs: a human running hive inside `tmux -L something` gets no auto-attach window. Correct rather than a regression - that window would have opened onto a server that is not theirs - and narrower than it reads, since a human inside that server is an attached client on it, so under `auto` the probe already returned first; only `on` ever reached the attach. Pinned by `test/auto-attach-scope.test.mjs`. Read its socket constants before adding a case there: the guard fails silently in BOTH directions, so the file pins two refusals (private through `TMUX_TMPDIR`, and private through `TMUX` as a real `tmux -L` pane produces) AND the ordinary no-tmux-environment case that must still attach. Each refusal asserts an empty probe log, which is what tells this guard's return from the other three. The first version had only the `TMUX_TMPDIR` arm, so "TMUX is set" and "the socket is default" were perfectly correlated across the file and a guard keyed on TMUX's mere presence passed everything while leaving the leak open in its main production shape - found independently in review, then reproduced by running that mutation.

**No shell does not mean no quoting.** Issue #117, measured against a real iTerm rather than assumed: despite running with no shell, iTerm's own "command" tokenizer strips single quotes and groups quoted spans exactly like a POSIX shell would, and never treats a bare `;` as a separator either way. `renderAttachCommand`'s shell-style quoting (`src/tmux.ts`) is therefore harmless on the iTerm branch and load-bearing on Terminal's `do script`, which really does run through the user's login shell, for every token `attachScripts` currently emits - session names and the resolved tmux path, both drawn from `shellQuote`'s safe character set. Do not read that as "one rendering always serves both, for any input": the equivalence is proven for that safe set, not for an arbitrary token (a project name, say) landing in these scripts later with characters outside it - measure again before trusting it further. Do not assume "no shell" means the two branches need different rendering either; measure before diverging them.

## Only one channel into a pane is shortened (todo 475)

The rule file's prohibition is short because the derivation is here.

**The measurement.** Over one evening, worker-to-lead `agent_send` text ran 440 to 1,516 bytes, average 885 across 8 messages. The other two lead-bound channels the same evening: standing-watch finish notices delivered at 72-90 characters (stored at 860-895 and shortened at delivery), and the lead's own `wake_set` bodies at 143 bytes, verbatim. One of three channels was unshortened and it was roughly ten times the shortened one. Most of those 885 bytes duplicated what the worker had already written to its todo.

**Why the threshold is 300 and not a round number.** The two populations leave an empty band from 144 to 439: nothing anyone has argued must arrive whole exceeds 143, and no real worker report is shorter than 440. 300 sits near the middle of that band, so neither a terser report nor a longer urgent line crosses by accident. Measured in characters, matching every other budget in the repo (`truncateBody`'s 120, `DESCRIPTION_BUDGET`'s 80); mixing units for one constant is how the next reader gets it wrong.

**Why the head is 140 and must not be trimmed.** A threshold alone only half-delivers the protection it exists for. A 450-character message whose first line is "BLOCKED, the machine is wedged" is exactly the urgent case, and an opaque pointer turns triaging it into a tool call. 140 is budgeted against the same 143, so a message of the class that must arrive whole survives as the head essentially intact.

**Why a new table rather than the hook's `agent_state_log`.** Its `prompt` payload holds the full text today only because the full text is what gets typed. Shorten before typing and the hook records the pointer, so the lookup would read something that was never written - the same failure as `dead-ends/2026-08-20-shortening-a-notice-at-write-time.md`, one step worse. Writing hive's own rows into that table instead was rejected separately: it has no `project_id` to scope a read tool by, and `state` is `NOT NULL` in the one column the table exists to record.

**Why the miss taxonomy exists.** The pointer line stays in a human's scrollback; the row is pruned at 7 days (plus a 5,000-row backstop, lower than `agent_state_log`'s 20,000 because a row here holds message text). So a pointer routinely outlives its message, and answering "not found" would read as a bug, a mistyped id and a scoping refusal at once. `AUTOINCREMENT` on the table is load-bearing for this: `sqlite_sequence` keeps the highest id ever issued after every row is deleted, which is the only thing that separates a pruned id from one that was never handed out.

**Why the receipt is fields on a success, not a tagged throw.** `decisions/2026-08-14-a-tagged-throw-not-a-structural-receipt.md` throws because that send genuinely failed. This one succeeded: the lead was reached and the text is durable. Telling a caller a delivery failed is what makes it resend, and the copies merge. `shortened: true` is the branchable token; the note is the only channel that can stop a worker writing 900-byte reports believing they were read.
