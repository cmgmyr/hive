# Patterns

Standing judgment calls this project has already made, distilled from the corpus of decisions and dead-ends recorded while building it: 53 decisions and 109 dead-ends at the time this was written, narrowed to the ones that are about how the code is built and still true today.

**`.claude/sessions/` is untracked, by Chris's own call.** A tracked file whose argument depended on an untracked directory would be a dead link for every reader but the one machine that has it. So every pattern below states its own reasoning in full; the source file it was distilled from is cited as provenance for anyone who does have the corpus, never as the only place the reasoning lives. A pattern with no citation is an opinion; a pattern whose citation is the whole argument is a broken link waiting to happen.

**What this document is not.** It is not a lookup for how a mechanism works; that is `docs/architecture.md` and `.claude/rules/*.md`. It is not review or process methodology: how many reviewers a round gets, when to run `/simplify`, how CI triage works. That material lives in `test/CLAUDE.md` and the project's runbook (`hive runbook`), and it is deliberately excluded here even though it is a large fraction of the corpus, because it is about how work happens, not about what the code is. And it does not cover refusals about machinery that no longer exists in this project, even when the reasoning was sound at the time.

## Trades this project makes on purpose

**Refuse rather than fall back, whenever a wrong guess would be silent.** State resolves strictly from the calling session's working directory: a `cwd` matching no registered project becomes its own new project rather than attaching to an existing one, and cross-project access happens only when a caller explicitly names another project. An earlier version auto-selected the one existing project when nothing matched, and a session in an unrelated directory silently read that project's todos. A convenience fallback and a coordination store are in tension whenever the fallback can be silently wrong, and the resolution here was to make the miss loud (a new, empty project) rather than plausible-looking (someone else's data). (`decisions/2026-07-16-strict-cwd-project-scoping.md`)

**Candor in the working record over publishability of the repo.** The corpus this document was distilled from is deliberately gitignored, a call Chris made once the tradeoff was visible rather than a standing policy anyone wrote down in advance. The material is candid about what was tried and rejected, including reasoning that reads badly out of context, and that candor is exactly what makes it useful to the next person and what makes publishing it a choice rather than a cleanup. The consequence is what this document exists to solve: a tracked file cannot cite it as its only argument. (`decisions/2026-08-02-session-corpus-stays-untracked.md`)

**Take the strictly-better option even when the measured win is small, as long as it costs nothing real.** `better-sqlite3`'s npm-synthesized install script is denied rather than approved, even though measurement showed identical end states either way on every platform this project ships for: same prebuilt addon, same working database, the only difference being whether a no-op `node-gyp rebuild` ran. Denying it closes one attack surface (arbitrary code at install time) for zero cost where a prebuild exists, and the decision says plainly where it stops helping: the prebuilt binary itself still loads unexamined, so this is a smaller claim than "we don't run untrusted dependency code." (`decisions/2026-08-06-deny-the-install-script-rather-than-approve-it.md`)

**A failure must not be shaped like a success.** When a paste lands but the following Enter fails, the tool throws rather than returning a receipt like `{pasted: true, submitted: false}`. A structural-looking receipt invites a caller to poll only the field that looks like success and read a botched send as fine, which is the exact failure slim receipts exist to prevent; a caller polling `sent` on a half-finished send is worse than one that has to notice a thrown error. The throw carries a stable bracketed tag so a caller can still branch on it without parsing prose. (`decisions/2026-08-14-a-tagged-throw-not-a-structural-receipt.md`)

**A config key needs hive's trust gate only if it can introduce a string hive didn't already know, not because of how much it affects behavior.** hive.yml has three shapes now. `processes:` commands are gated because each one is an arbitrary string hive later `execFileSync`s verbatim - the repo controls literal bytes that run. `vars:` are deliberately ungated because they carry arbitrary strings that reach a system prompt as text and are never executed - the repo controls prose, not code. `agents:` is neither: every entry is checked at parse time against `harnessNames()`, a fixed, code-defined table, and dropped with a warning if it isn't one, so the repo can only ever pick among names hive's own code already recognizes - it can narrow what hive spawns and can never widen it, which is why it needs no gate. The test generalizes past this one key: a key that selects from a closed set the code owns is safe ungated however much it affects behavior; a key that passes a value through to execution needs the gate however harmless it looks. (todo 526, comment 1802)

## Approaches already refused

**Gating only the read side of a cross-server guard.** `liveTargets()`/`targetLive()` refuse reading tmux state when hive is on a private socket paired with the default store (`.claude/rules/tmux-and-panes.md` covers why that pairing is refused at all); an early version left `launchAgent`/`ensureSession` ungated on the theory that a spawn there is untidy but not damaging. It was not true: under that pairing, `ensureSession` cannot find the real session on the private server, creates a second one there, and the pane id from that fresh server gets written into the shared store. A fresh tmux server numbers panes from zero, so the recorded id is very likely to collide with a real pane belonging to someone else on the shared server, and `agent_send`/`agent_close` will act on it. The general trap: a path that only creates things can still destroy something, because what it creates is an identifier a different process, on a different server, will later trust. The fix landed once, in the one function that creates a session, rather than at every caller. (`dead-ends/2026-07-29-spawning-under-the-bad-pair-is-harmless.md`)

## What counts as evidence here

**A proposed fix inherits its proposer's framing, and every check that starts from the proposal inherits it too.** Measured across one real defect: a review found a scheduler claim missing an optimistic-concurrency guard, a worker implemented the guard and caught one real bug the reviewer's framing missed, the lead signed it off, a second automated pass re-reviewed the fixed code and found nothing, and a fifth, independent read then found the fix was still wrong on two of three fields the reviewer's framing had never named. Four checks passed a fix that was wrong, and none of them was careless: each one verified the fix against the framing that arrived with the defect, because the framing does not look like a claim that needs its own verification. The standing rule: whoever certifies a fix must not be the reader who proposed it, and must re-derive the invariant from the code rather than from the proposal's description of it. (`decisions/2026-08-03-a-fix-inherits-its-proposers-framing.md`)

**A number produced by a pattern written for the audit measures the pattern, not the codebase.** An ad-hoc `grep -oE` swept for stale counts in the docs and produced two confident, wrong answers: "0 registered MCP tools" from a pattern that missed every real call site, and a phantom discrepancy in a CLI command count caused by not deduplicating multi-form commands in `hive --help`. Re-deriving both with the project's own parser gave the right numbers, one of which turned out to match the docs exactly. A number worth reporting is derived from the same code the product or the suite uses to produce it, or pinned by a test; a number produced by a bespoke one-off pattern is not evidence, whatever it claims to measure. (`dead-ends/2026-08-10-ad-hoc-greps-to-audit-numeric-claims.md`)

**A mechanical check can be blind to exactly the failure it was built to catch.** Verifying that a prose rewrap changed only line breaks, by diffing the sorted multiset of whitespace-separated tokens before and after, is a genuinely strong check, and it is provably blind to a token that a line break had split and a rewrap rejoined with a space instead of nothing: `tmux-and-panes` + `.md` on two lines and `tmux-and-panes .md` on one line are the same two tokens to a multiset, so the check passed over a broken path to the exact rule file governing the code the broken comment sat in. `git diff --word-diff` is blind to the same class for the same reason. A single mechanical check earns trust for the class of error it was built to catch, not for adjacent classes it happens to also touch; this document's own citations were checked by reading the target, not by a rewrap-style diff. (`dead-ends/2026-08-15-token-multiset-blind-to-rejoined-tokens.md`)

## How a guard is expected to be shaped

**An append-only log for anything a later reader needs to trust a sequence, not a single overwritten row.** Worker liveness used to be one `agents.agent_state` column, overwritten on every hook call. A false `idle` was written and self-corrected two seconds later; a lead sampling the row a minute later saw a healthy value and recorded a pass on a lane that had already failed. `agent_state_log` adds one append-only row per hook invocation, and the fix is not "poll more often" but "read the sequence": the same self-correcting bug is invisible to any sampling frequency and obvious to one query over the log. The column recording which event wrote the state was added for a second reason: two people had already reasoned from "an idle was written" to "the stop event wrote it" without checking, when the true writer was a different branch entirely. (`decisions/2026-07-29-append-only-state-transition-log.md`)

**A rule enforced at the one choke point a system already has, not swept across every call site that uses it.** Every MCP tool's input is made strict by wrapping tool registration once, in the single place all 42 (at the time) `registerTool` calls pass through, rather than editing each call site to opt in. A rule enforced by sweeping N call sites is correct until the N+1st one is added by someone who does not know to repeat it; a rule enforced at a real choke point is enforced automatically. The guarantee is only as strong as what checks it, so a test walks the tool surface the server actually generates rather than trusting that the wrapper was applied — an earlier version of that same test only checked the top-level object and missed a nested parameter reintroducing the bug one level down. (`decisions/2026-08-07-strictness-at-registration-not-at-the-call-sites.md`)

**A check that can fail declares up front whether its failure should be fatal, and the default is not fatal.** `hive doctor --strict`'s exit code is gated only by warnings that opt in as `gatingWarn` rather than the ordinary `warn`; everything else still prints and still counts on the summary line, but cannot change the exit code. The first version gated every warning, and it broke the thing it was built for: `--strict` was meant for an update script to gate on, and it failed on any machine in a state that is normal but imperfect, including the exact machines the feature existed to protect. Making the default non-gating means a warning a future change adds cannot break somebody's script unless its author deliberately opts it in. (`decisions/2026-08-07-strict-promotes-only-gating-warns.md`)

**A cautionary counter-example: splitting one hold-reason value into two so a caller can tell "unclaimed" from "claimed but unreported" flapped, because the fallback write path and the value it was gating on were not kept in lockstep.** The design added `UNREPORTED`/`REPORTED` constants for a scheduler hold state, gated the winning path on `!== REPORTED`, but the losing (fallback) path wrote its own value unconditionally, with no predicate matching the gate. Three ticks reproduced the bug: a claim wins and writes `REPORTED`, the next tick's fallback overwrites it with `UNREPORTED` because nothing stopped it, the tick after that reads `UNREPORTED`, matches the gate again, and re-fires a notice that had already been sent. Splitting a value into "reported" and "not yet reported" variants only holds if every writer of that value, including the ones added later, is gated by the same predicate; a single caller keeping the invariant is not enough. (`dead-ends/2026-08-14-two-hold-reason-constants-to-make-a-claim-refusable.md`)
