
# test/CLAUDE.md

The incidents, measurements, and worked examples behind `test/CLAUDE.md`'s prohibitions. Each is enforced by code and pinned by a test; the prohibition tells you what to do, this tells you why.

## What the guards do not cover

- **`isolateTmux()`'s `cleanup()` kills sessions only, and only by name.** The socket directory is removed once on process exit. It used to be removed per-`after()`, so a file with more than one tmux `describe` destroyed its own isolation halfway through: `TMUX_TMPDIR` went on naming a path that no longer existed, tmux does not create it, and every later `describe` silently created sessions on the developer's own server.
- **The exit handler kills the file's own tmux SERVER, and reports any session it had to reap.** Because `cleanup()` reaches a session only by name, anything never threaded through a `cleanup(...)` call used to outlive the file: `new-session -d` on a cold socket forks a server that `setsid()`s into its own session, `ps` keeps showing the original `new-session` argv forever (fork carries argv with no exec, so it reads as a stuck client and is not), and the `rmSync` below then deletes the directory backing that server's own listening socket. The server stayed alive and unreachable. One per full-suite run, 227 alive at one point, and a run eventually died with `fork failed: Device not configured`. The handler now runs `list-sessions` first and names anything left, setting `process.exitCode = 1` so the file that leaked is identified rather than an anonymous pid found later.
- **The exit handler VERIFIES its own kill, and keeps the socket directory when the server survived.** `kill-server` is bounded (`timeout: 5000`), so it can now return having achieved nothing against exactly the wedged server that bound exists for, and an unverified kill reads identical to a successful one. The handler re-probes the socket afterwards; on a survivor it names it, sets `process.exitCode = 1`, and SKIPS the `rmSync`. **A survivor is anything the probe did not prove gone**: only tmux's own answers - `no server running on <path>`, `error connecting to <path>` - mean nothing is listening, and a probe that could not RUN (EAGAIN, EMFILE: the fd exhaustion this detector exists to catch) keeps the directory too. Reading a failed spawn as "gone" is what let the handler delete a live server's socket file. The four socket states, measured, are in `docs/attic/scripts__tmux-leaks.mjs.md` under `probeScratchSocket`; the load-bearing one is that `kill-server` does NOT unlink the socket file, so a reaped socket answers rather than vanishing. Removing the directory deletes the socket file backing that server's own listening socket, which is what made the leaks above unreachable forever: alive, holding ptys, impossible to name. One scratch directory is the price of keeping it reapable by hand and visible to `hive doctor`'s orphan report.
- **`npm test` runs `scripts/run-tests.mjs`, which asks every socket the run created whether a server is still on it.** `isolateTmux()` appends its socket to `HIVE_TMUX_LEAK_MANIFEST` at CREATION time, because a file killed before its handlers run leaves a server nothing in that process will ever report - node does not run `process.on("exit")` under a default-disposition SIGTERM (measured). **The manifest path is read once at helpers-module load, never from `process.env` at call time**: `clearHiveEnv()` deletes every `HIVE_*` key including that one, so a file that cleared first and isolated second used to drop its own socket while the run still reported every socket it did receive as "all gone". The check runs after every file has exited, cannot turn a red run green, and reports a MISSING manifest as a failure rather than as a clean run. **A file that starts a server on a SECOND, bespoke `TMUX_TMPDIR` must call `recordScratchTmuxSocket(tmuxSocketUnder(dir))` itself**: `isolateTmux()` appends only its own socket, so those servers were invisible to this check and to the `ps` guard at the same time (four files do it - `probe`, `lead-data-dir`, `tmux-socket`, `isolated-hive`). Register at creation, not at teardown, for the same reason. A bare `node --test test/one.test.mjs` sets no manifest and stays silent, which is why a single-file run is still a normal thing to do. **`npm test -- <file>` is the other single-file shape and it does set one**: there the missing-manifest failure is relaxed, because the file list is the caller's rather than the runner's and plenty of legitimate targets never touch tmux (`npm test -- test/db.test.mjs` exited 1 on a clean pass until the PR gate caught it). A real leak still fails a named run; only the manifest's ABSENCE is forgiven. Its own coverage gap is a server whose socket file is already gone, which is what the exit handler above now avoids creating, and what `scripts/tmux-leak-guard.sh`'s coarser `ps` net still exists for. Pinned by `test/tmux-leak-check.test.mjs`, proven red against a real leaked server and against the whole runner.

## The CI matrix: the `alt` pairing and the OS split

`alt` is paired explicitly rather than derived, because the only thing that makes an alt VALID is that its NODE_MODULE_VERSION differs from `node`'s (test/helpers.mjs alternateInterpreter). A rule like "always 22" silently stops discriminating on the leg where 22 IS the primary, and the tests that need it would skip while still reporting green.

THE OS SPLIT WAS A BILLING DECISION, AND STILL IS - THE CONCLUSION CHANGED, THE REASONING DIDN'T (todo 350). A private repo bills macOS at 10x, so a macOS job that really takes 2.6 minutes is charged 26. Two macOS legs were 1,360 of this account's 1,425 billed minutes in the first four days of August. A later sample of the 30 most recent CI runs measured the same shape at larger scale: macOS was 77% of billed minutes (28 jobs, 150 wall minutes, 1,504 billed) against 413 for both Linux legs combined and 31 for floor-boundary - macOS ran FEWER wall minutes than Linux (5.37 vs 7.38) and still cost ~3.5x both Linux legs combined, purely from the multiplier. That is what moved macOS off every push and every PR and onto the weekly canary below (`test-macos`): the platform coverage is the same, the price of getting it on every commit was not buyable at the moment this was decided.

Linux carries both Node versions, which is where the version signal the comment above argues for actually comes from. This job no longer carries a macOS leg at all - `test-macos` below is where "hive is a macOS tool and the native addon builds there" now lives, on its own schedule.

## The attach/view-race fixture: three things that made it pass while proving nothing

`test/attach-view-race.test.mjs` drives two real tmux clients against one base session. Three of its choices look arbitrary and each is load-bearing.

**It uses `-C`, not the product's own `-CC`.** The second `C` disables echo and needs a real terminal, so a headless `-CC` client dies with "tcgetattr failed" and attaches nothing at all - a test that passes while proving nothing. Control mode here is only the transport that lets a client exist without a tty; whether hive passes `-CC` is `controlModeFor`'s question and `test/attach-mode.test.mjs`'s. The client is kept alive across the observation by the test process staying alive, because a client whose stdin pipe closes detaches and ends the very state being observed.

**Each child waits for its OWN client, never for the peer's.** An earlier version waited for both views to exist at once and was flaky under a loaded suite: each child kills its client when it finishes and `destroy-unattached` takes its view with it, so "both alive at the same instant" is a rendezvous between two processes with no reason to be in step. Each child proving its own attach landed on its own view is the same claim without the coupling, and the peer's independence is then just the two reported names differing, which the parent checks.

**The `list-windows` and `show-options` reads exist because every other assertion in the file was blind to grouping** (issue #117, review finding F4). A mutation dropping `-t =<base>` from the created session - making it standalone rather than GROUPED with base - passed every assertion in the file before those two reads: each was a regex over the emitted string or a client-location probe, and neither can tell a grouped view from an ungrouped one merely named the same shape. `list-windows` on the view is the only way to prove grouping means anything, and `show-options` reads whether `destroy-unattached` TOOK EFFECT rather than that the string asking for it was built.

**`show-options -t` does not accept the `=` exact-match form** the rest of that file's targets use. Measured: it throws "no such session" against a real, live, client-attached view where `has-session`, `list-clients` and `list-windows` all succeed. The bare target there is deliberate, not an oversight.
