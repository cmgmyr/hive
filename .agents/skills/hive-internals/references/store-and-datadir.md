One of these was broken on 2026-07-28 and destroyed every `agents` and `timers` row in the developer's live store. Each is enforced by code and pinned by a test.

## The data dir is read at call time and cached in exactly one place

`src/dataDir.ts` used to hold it in a module-level `const`, which resolved once at that module's first load. A static `import` of a `dist/` module at the top of `test/helpers.mjs` was hoisted above the line setting `HIVE_DATA_DIR`, so the const had already taken `~/.hive`, `dist/db.js` agreed with it, and the suite's `DELETE FROM timers; DELETE FROM agents;` ran against the live store.

It now reads the env when asked and caches nothing, so importing a module no longer decides the store for a process that has not opened one.

Be precise about what that does NOT fix: `src/db.ts` still opens the database in its module body, so importing `db.js` is itself the act of choosing a store. That is the remaining debt. `db.ts` keeping a `const` is fine, because it only writes down a commitment the module already made.

`resolveDataDir` is deliberately NOT exported. It is `storeDir()` with the refusal removed, and exporting it would put the one call that reintroduces this whole class of bug into the public API, shorter than the guarded one and reading more obviously correct.

**Issue #81's `src/config.ts` is a second consumer of this reasoning, not a special case.** `attachMode()`/`setAttachMode()` resolve `storeDir()` inside the function body on every call, for the identical reason `dataDir.ts` does. One place it diverges deliberately: a config READ (an absent or malformed `config.json`) never throws, defaulting instead, because a config read must not be the thing that breaks a tmux attach. `storeDir()`'s OWN refusal (the test-isolation guard right above) is not folded into that default -- it is left outside the try in `readConfig()` so it still reaches the caller, the same as it already does on the write side. Swallowing it too would make a misconfigured test process read a silent default instead of the loud failure this guard exists to give it.

Only the COMPARISON canonicalises symlinks. `resolveDataDir` keeps returning the path as the caller named it, because that string also builds brief and posture files, and rewriting it to `/private/var` on macOS changes paths callers hand back to hive.

## Test isolation is enforced, not conventional

`CLAUDE.md` used to assert "real data stays untouched" as a property. That was a convention held up by every author remembering a rule, and it was false on the day it mattered. Three guards hold it up now and all three must stay.

- `storeDir()` refuses `~/.hive` outright when a test runner is the entry point, keyed on `NODE_TEST_CONTEXT`. That is an env var, so it crosses into every process the suite spawns, and a file that never sets `HIVE_DATA_DIR` fails loudly instead of writing to a live store. It throws for mid-command callers; `db.ts` uses `guardStoreDir()`, which prints and exits for the same reason `guardAbi()` does, since a throw out of an ESM module body arrives as a stack trace with hive's sentence buried in it.
- `storeDir()`/`guardStoreDir()` also refuse `~/.hive` for any process that is not one of hive's own entry points, checked whether or not a test runner is involved (below).
- `test/suite-isolation.test.mjs` reads the suite's own source and fails when a file that can reach tmux does not call `isolateTmux()` at module top level.

None of the three can tell one scratch directory from another, so `assertScratchStore()` still earns its place in a destructive file. `test/store-isolation.test.mjs` reproduces the original mistake and pins all of it. The rest of the suite's rules are in `test/CLAUDE.md`.

**That USED TO cover only the SUITE, and the runbook requires every lane to write something none of the three guards above could see.** Step 11 - exercise the change against a real server rather than the tests - is a hand-rolled driver script, and the original three guards missed it: `storeDir()`'s test-runner refusal keys on `NODE_TEST_CONTEXT`, which a plain `node driver.mjs` does not set; `assertScratchStore()` is a helper such a script never calls; and `test/suite-isolation.test.mjs` reads the SUITE's own source, so a driver outside `test/` is invisible to it. The mechanism is the one stated above, reached from the other side: **`src/db.ts` opens the store in its module body from the CALLING process's environment, so `await import(dist/db.js)` IS the act of choosing a store.** Setting `HIVE_DATA_DIR` in the env you hand a CHILD process does nothing for the parent that imports `db.js` to seed or inspect rows - which is the natural way to write such a driver, because a scratch store starts empty and the thing you are exercising usually needs a row in it.

This happened for real: that driver once ran `UPDATE agents SET agent_state = 'waiting' WHERE name = 'impl'` against `~/.hive`, the live store. It changed nothing only because no live agent happened to be named `impl` - a name this project uses constantly.

**Closed with a fourth check rather than another paragraph.** `defaultStoreRefusal()` (`src/dataDir.ts`) now refuses the default store for any process that is not one of hive's own five scripts - the CLI, the MCP server, the Claude Code state hook, and both of the SessionStart kickoff entries (`dist/kickoff.js` and the plugin's own `claude-plugin/kickoff.mjs`, which lives outside `dist/` and runs first) - identified by `isProductEntryPoint()` comparing `process.argv[1]`, set by node before any user code runs, against each script's resolved path. A hand-rolled driver is none of those, so it is refused the same way a test runner is, through the identical printed-and-exited `guardStoreDir()` path, and the message it gets names the one legitimate case the check cannot see: `HIVE_ALLOW_DEFAULT_STORE=1`, a deliberate opt-in for a human's one-off script. That override cannot reach the test-runner refusal - `defaultStoreRefusal()` checks `underTestRunner()` first and returns before the override is ever consulted - because the point of the override is a human at a terminal, never a test process that happened to set it. `test/store-entry-guard.test.mjs` pins the whole thing, including that a test-runner process cannot use the override to defeat its own refusal.

The preamble below still applies to a driver targeting a SCRATCH store, which the check above cannot see at all - it only ever judges the default store - so it earns its place for the same reason `assertScratchStore()` does: neither guard can tell one scratch directory from another.

```js
process.env.HIVE_DATA_DIR = scratchDataDir;   // BEFORE any dist import
const { db } = await import(join(DIST, "db.js"));
if (!db.name.startsWith(scratchDataDir)) throw new Error(`refusing: opened ${db.name}`);
```

The refusal is the load-bearing half, since the assignment can be defeated by an import that is hoisted above it - which is the original 2026-07-28 bug in a new file.

A symlink pointing at `~/.hive` is the case that defeats both guards at once, which is why the comparison follows symlinks: `storeDir()` would not refuse it under a test runner, and `untrustedTmuxServer()` would read "scratch store" and let a private tmux server write pane ids into the live database.

**A THIRD hole in this story, and the one no store guard could ever have closed.** Full isolation - scratch `HIVE_DATA_DIR`, private `TMUX_TMPDIR`, `TMUX` unset - still leaked a session, a control-mode client and a native terminal window onto the developer's own tmux server on every `agent_spawn`, because `ensureAttached` opens that window through AppleScript and the GUI shell it spawns inherits none of this process's environment. Every guard on this page is about which STORE a process opens, and the store was correct throughout: the damage went out through a different channel entirely.

Closed on a SOCKET predicate, `privateTmuxSocket()`, never on the store - stated here because this page is where a reader would expect the store-shaped fix, and it would have been the wrong one. A refusal keyed on "`HIVE_DATA_DIR` is not the default" reads as obviously right and deletes its own test method: a scratch store on the DEFAULT socket is the only way anyone here has found to reach `ensureAttached`'s interesting branch at all, since a live session always has a client and returns early. Mechanism, cost, and the reason the fix must prevent the CLIENT rather than re-point it: `.claude/rules/tmux-and-panes.md`.

One consequence for anyone writing tests here: `isolateTmux()` sets that private `TMUX_TMPDIR` in the TEST PROCESS's own environment, so every file calling it runs with `privateTmuxSocket()` true. Before the fix above, that made `test/auto-attach-scope.test.mjs`'s two "a window opens" cases assertions about the LEAK configuration while reading as assertions about the ordinary one. They set the socket explicitly now. A fixture's third dimension being invisible because nothing reads it is a shape worth checking for, not a one-off.

## Migrations are append-only

Never edit an existing entry in `MIGRATIONS`; add a new one. A snapshot is taken before any pending migration runs, which is one of the two backup triggers.

**A trigger migration adds a standing constraint on every migration after it.** `pads`, `todos` and `kv` each carry a SQL `BEFORE UPDATE` trigger that aborts when a content column (`pads.content`, `todos.title`/`body`, `kv.value`) changes while `updated_at` does not read as the current moment. Any future migration that rewrites one of those columns for existing rows must stamp `updated_at` in the same `UPDATE` statement, or it aborts against its own trigger. This cannot be relaxed retroactively once a store has applied the migration, since migrations are append-only - know this going in, not after a migration fails against a store that already has it.

## The store's write lock now also excludes something that is not a store write

`withWindowClaim` (`src/spawn.ts`) is `db.transaction(claim).immediate()` wrapped around a section that reads whether this store's shared tmux session already has a window for a project and, if not, creates and stamps one - a tmux operation, not a database write. It works because of the exact fact this file already rests on: every hive instance on a machine shares one WAL-mode SQLite database, and SQLite allows exactly one writer at a time. `BEGIN IMMEDIATE` takes that writer slot up front rather than on first write, so a section that writes nothing to the database still excludes every other `withWindowClaim` section on the machine from running concurrently. `launchAgent`, `cmdLead`, and `cmdAttach` (`src/spawn.ts`, `src/cli.ts`) all wrap their own read-then-create window sections in it, which is what stops two concurrent creators from both stamping a window for the same project - the store's write lock, borrowed to serialize something outside the store.

Two rules on what may live inside that section, both because the thing being borrowed is the store's ONLY writer slot, shared by every hive process on the machine:

- **Tmux forks only, and only fast ones.** The section holds the lock for as long as it runs; `db.ts`'s 5s `busy_timeout` is four orders of magnitude more than the few tmux forks a window claim actually costs, and the scheduler's `tick()` (above) contends here like anything else on the machine.
- **Never anything that blocks on a human.** A prompt inside this section would hold the store's only writer slot hostage to someone reading a terminal, stalling every other hive process on the machine until they answer. This is the identical failure shape the residual directly below warns about for restore - a process spanning a human-blocking prompt - one level up: there it is about a stale file descriptor surviving past a prompt, here it is about a lock. `hive.yml`'s trust prompt is the concrete near-miss: `ensureTrusted` runs well above `cmdLead`'s own claim call, never inside it.

**The hazard that would remove the exclusion with nothing failing, now refused rather than merely watched for.** better-sqlite3 nests a transaction inside another one via `SAVEPOINT` rather than throwing. A `withWindowClaim` call made from inside an already-open, `DEFERRED` outer transaction would take no writer slot of its own - it would ride along inside the outer one as a no-op savepoint - and the read-then-create race this function exists to close would be back, with no error and nothing in the suite going red to say so. This was only checked at review, not enforced: every `db.transaction` call in `src/` that could run before a `withWindowClaim` call site was confirmed to sit outside it (`ensureLeadRow`'s two, `src/cli.ts`, both run before `cmdLead`'s own claim; the lead-pane CAS runs after it). A review-time check protects only the code as it stood that day, and if a future caller wrapped its own call to `launchAgent`, `cmdLead`, or `cmdAttach` in a transaction, this is what it would have broken, silently - the same class of hazard `storeReplaced()`'s open-to-stat window is, below. `withWindowClaim` (`src/spawn.ts`) now throws on `db.inTransaction` before `db.transaction` is ever entered, so nesting gets a loud, explanatory refusal instead. Pinned by `test/window-claim-guard.test.mjs`.

**One caller now opens a transaction of its own in the same function that later reaches `withWindowClaim`, and it is safe for a reason worth stating rather than rediscovering.** `resumeAgent` (`src/spawn.ts`) wraps its capture-then-flip in `db.transaction(...).immediate()`, because the flip destroys the values its own failure path has to restore and SQLite's `RETURNING` yields post-update values only. That transaction COMMITS before `placeAgentPane` runs, so the `withWindowClaim` inside it takes a real writer slot exactly as before. Two statements and no forks, which is what keeps it inside the "fast only" rule above. If a future edit moves the pane creation inside that transaction, the refusal fires loudly rather than silently degrading the claim - which is the whole point of the guard, working as designed on the first caller to make the shape reachable.

Same two honest limits as any other user of this lock, restated here because they read differently once the thing inside the section is tmux rather than SQL: tmux side effects do NOT roll back with the transaction - a throw partway through leaves whatever windows were already created; the lock buys mutual exclusion, not atomicity. And a process that dies inside the section releases the lock, since SQLite rolls the transaction back on connection loss, which is why this is a transaction and not a leases-table claim with a TTL to get wrong.

## Restoring a live store orphans every open connection

`restoreSnapshot` renames the new file into place, which is atomic and correct, but it cannot reach into a process that already opened the old one. That process keeps its file descriptor, pointing at an inode with no name. Both are `~/.hive/hive.db`, neither errors, and (without the guard below) the orphan is freed when the last descriptor closes, so the work is destroyed at the moment the session ends having looked fine throughout.

`hive restore`'s own refusal reads two live signals, a running `agents` row or a `hive-*` tmux session, and `--force` skips both. Read `--force` as "I have accepted this outcome", never as "I am fairly sure nothing is running": it cannot see a `claude` session started outside hive, or one starting in the gap between the check and the overwrite.

**Issue #49: an MCP server now detects this itself and refuses, rather than silently continuing.** `storeReplaced()` in `src/db.ts` records the inode `db` opened right after `new Database`, and a fresh `statSync` on every call compares against it - once tripped it latches, since the answer cannot change back. Two guarded entry points cover the server's whole write surface: `run()` in `src/result.ts`, the choke point every registered tool routes through (pinned by `test/tool-registration.test.mjs`, which scans `src/tools/*.ts` and fails if a future tool's handler does not call it), refuses every call, reads included, and names the remedy (restart the session). `src/scheduler.ts`'s `tick()` checks the same predicate and, if tripped, stops permanently rather than throwing (`CLAUDE.md`'s "the scheduler must never throw" holds) - an orphaned scheduler's harm is not the store, it is typing a stale wake into a live tmux pane as a real user turn.

Manual diagnosis is now the fallback, useful for a server predating this guard or when reading the situation from outside a poisoned session: `stat -f %i ~/.hive/hive.db` against the inode in `lsof -c node | grep 'hive.db$'`. Disagreeing inodes are the diagnosis. Recovery means REPLAYING writes into the new file from a fresh process, then restarting the session.

**Two known residuals, both accepted rather than fixed here.**

- **The open-to-stat startup window.** `storeReplaced()`'s baseline is read right after `new Database`, not atomically with the open itself. A rename landing in that gap makes the new process record the NEW inode as its own baseline, so it never sees a mismatch for a replacement it never actually observed - the failure mode is silent, same as with no guard at all, not worse. The clean fix needs `fstat` on the open descriptor, which better-sqlite3 does not expose. Module-load code already carries two documented startup races (see `db.ts`'s WAL-conversion retry); adding a retry loop here for a narrower window than either of those was judged not worth the risk of breaking every hive process at startup over a residual that is no worse than the pre-#49 baseline.
- **A CLI process blocked on an interactive prompt is not guarded.** The claim elsewhere in this codebase that every non-server writer is short-lived, and therefore cannot hold a stale inode across a restore, has exactly one exception: `hive lead`'s `hive.yml` trust prompt and `hive init` open the store at load and write after a prompt that blocks on a human, so that process genuinely can span a restore. Known and unfixed; do not repeat the unqualified "every non-server writer is short-lived" claim without this caveat.

## A PreToolUse hook denies a raw SQL write to the store's database file, and knows its own limits

Todo 331: one project's board held another project's board content. Traced to a session in hive's own checkout running, twice, `UPDATE scratchpads SET content=?, revision=revision+1 WHERE name='board'` with no `project_id` predicate. Pad names are unique PER PROJECT, not globally, so `WHERE name='board'` matched every project's board; hive's own row happened to already hold hive's own content, so only the other project's was overwritten. Found by grepping the session transcript for the statement itself, not by reading `updated_by`/`updated_at`, both of which still named the victim and a time 47 minutes earlier - the writer skipped the very columns that would have identified it (todo 331 comment 707).

The `BEFORE UPDATE` trigger under "Migrations are append-only" above closes the same-writer class this incident belongs to, but leaves two shapes open by construction: a write that stamps `updated_at` correctly but carries no `project_id` predicate at all, since nothing at the database level can require a WHERE clause to be selective; and a raw rewrite landing in the SAME wall-clock second as the row's own last legitimate write, because the trigger compares against `datetime('now')` at second resolution and both reads return the same second. Worse, the trigger's own error message NAMES `updated_at`, so an agent told to fix its statement complies and lands on exactly the incident's shape. A negative-control test (`test/store-write-trigger.test.mjs`) asserts the same-second bypass still succeeds today, so it goes red the day anyone narrows the window rather than staying a prose claim.

`scripts/store-write-guard.mjs` closes both from a different layer: it denies a Bash command before it runs, when a home-relative default-store path ending in the database file itself (`~/.hive/hive.db`, `$HOME/.hive/hive.db`, or the resolved homedir spelling - never the bare `.hive` directory, since `profiles/`, `backups/`, `briefs/` and `postures/` live under it too and reading them is not a write) and a SQL-shaped mutation (`UPDATE [OR ...] <table> SET`, `INSERT [OR ...] INTO`, `DELETE FROM`, `CREATE TABLE`, `DROP TABLE`/`INDEX`/`TRIGGER`/`VIEW`, `ALTER TABLE`, `REPLACE INTO`) both appear ANYWHERE in the command, plus a separately correlated check for `rm` of the database file itself.

**It does not segment the command at all, and that is the second version of this guard, not the first.** The first version split on `;`, `&` and `|` so an unrelated write in one clause could not combine with an unrelated store mention in another - reasonable-sounding, and wrong. `;` and `|` inside a single shell argument CORRELATE a producer with the database consumer rather than separate unrelated commands: `python3 -c "import sqlite3; c=sqlite3.connect('~/.hive/hive.db'); c.execute('UPDATE scratchpads SET content=1')"` is ONE command, the path and the statement joined by `;` inside one quoted argument, and splitting on `;` put the path and the statement in different fake segments so neither alone matched - the exact incident, written as a one-liner instead of a heredoc, sailed through. Piping (`echo "UPDATE ..." | sqlite3 ~/.hive/hive.db`) failed the same way through `|`. The false-positive protection segmentation was built for was never doing the work credited to it: the `.db`-suffix requirement and the SQL-shape patterns already exclude every false positive segmentation was added against, checked case by case rather than assumed. Whole-command matching is what actually catches the incident; do not reintroduce segmentation without re-deriving this.

**Say this the way the tmux guard below says its own limit: a guardrail against a confused agent, not a security boundary.** It reads one Bash command string with no shell parser behind it, so it cannot see: a node driver importing `dist/db.js` directly, with no store path anywhere in the command string it runs under; `cd ~/.hive && sqlite3 hive.db ...`, since the `sqlite3` clause carries no home-relative marker of its own; SQL arriving by redirect or file (`sqlite3 ~/.hive/hive.db < x.sql`); `rm -rf ~/.hive` removing the whole directory rather than the database file the `rm` check is scoped to; or the escape hatch, `HIVE_ALLOW_DEFAULT_STORE=1`, matching anywhere in the command including inside quoted prose that happens to spell it, or on an unrelated earlier clause that unblocks an unrelated raw mutation later in the same compound command - anchoring it to a real environment-prefix position broke the ordinary `export X=1 && cmd` idiom in testing, so it stays loose. The cost runs the other way too, now that nothing is segmented: a live-store READ on one clause and an unrelated WRITE to a different, scratch database on another are denied together, which the denial message calls out directly (split the two into separate Bash calls) rather than leaving a reader guessing. None of this makes a cross-project write impossible; it narrows one door among several, the same way `tmux-kill-guard.mjs` narrows one door onto `kill-server` (`.claude/rules/tmux-and-panes.md`, and this skill's own `tmux-and-panes.md` reference, "Never run `tmux kill-server`").

**Both guard scripts had the identical fail-open entry-point bug, closed together.** `import.meta.url === \`file://${process.argv[1]}\`` compares a realpath-resolved URL against a raw argv path, so invoking either guard through a symlink - unremarkable in this repo, which runs leads inside `.claude/worktrees/<slug>` - makes the comparison false, skips `main()` entirely, and the process exits 0 with no output: indistinguishable from a clean pass. Fixed in both to `realpathSync(process.argv[1]) === fileURLToPath(import.meta.url)`, and pinned in both test files by invoking the guard through a real symlink rather than only calling `classify()`, since `classify()` cannot see this class of bug at all - it lives entirely in the wrapper. `scripts/store-write-guard.mjs` has a second fail-open path worth the same honesty: malformed stdin now exits 0 through a caught `JSON.parse`, deliberately - denying on a payload shape the guard does not recognise would block every Bash call the day Claude Code changes that shape, and this hook is the second line of defence (the trigger above is the first), not the only one. `classify()` never checks `tool_name` either; the guarantee that it only ever sees a Bash command rests entirely on the `"Bash"` matcher in `.claude/settings.json`.

## The teardown record, and why it is a file rather than a table (todo 450)

Four crew-wide tmux deaths - 2026-08-11 twice, 2026-08-14 twice - each took every pane on the shared server, including a second project's lead. **Exactly one was ever attributed**, and only because the guilty command happened to sit in a transcript someone was already reading. On the best forensic night this project has had, one death was named in about ten minutes and the other still is not.

**The premise the todo was written on was wrong, and it decided the design.** It read "hive is not on that path - it is the thing being killed", and concluded the breadcrumb had to be written on the way out. hive is not on the path of the KILL, but it is on the path of the DEATH: `janitor()` probes every running non-lead row and closes the ones whose pane is gone, and `liveTargets()` returns an EMPTY snapshot rather than `null` when the socket has no panes (`src/tmux.ts`, `tmuxSaysNothingThere(e) ? snapshot : null`), so a dead server yields "every pane on this socket is false" - the crew-death signature, already computed, on a branch that already existed. `hive doctor` from a plain terminal after a death, which is what a human actually does, is a working detector: it printed `N dead agents closed` and discarded every fact about them in the same statement.

**Write-on-the-way-out was rejected on REACHABILITY, not cost.** hive's entire tmux teardown reach is `kill-pane` (`src/spawn.ts`, `src/cli.ts`) and `kill-window` (`src/tools/agents.ts`); there is no `kill-server` or `kill-session` anywhere that hive executes - the two occurrences in `src/cli.ts` are text hive PRINTS for a human. So an on-exit breadcrumb can only ever record a single-agent close, which the `agent_close` receipt already attributes, and structurally cannot record the case the todo exists for.

**A continuous mirror was rejected too, and the reason is the transferable part.** To bound WHEN a death happened you need last-known-alive, and the plan assumed that meant refreshing a durable record as the crew changes. It does not: `agents.state_changed_at`, `agents.created_at` and `agent_state_log`'s newest row per actor already carry it, so the bound is derivable at detection time with no periodic write anywhere. The only thing a heartbeat would add is the distinction between a witnessed death and an inferred one - and that is in-process state (`socketLastSeenAlive`), not a durable write.

**Why a file and not the store.** A tmux server is a MACHINE-level object whose death crosses projects, which is the whole point of "including a second project's lead"; `kv` is project-scoped and TTL'd. `agents` cannot hold it because `RESUME_FLIP_COLUMNS` clears `closed_at` on the first resume - that is how the one piece of hard attribution evidence this project ever had was destroyed (todo 368 comment 1088). `agent_state_log` was refused because `src/stateProvenance.ts` and `src/dashboard.ts` both read "newest row for this actor", so a synthetic row moves what they report. `backup.ts`'s snapshots are precedent for a non-DB artifact in the data dir, so this is not a new class.

**The resume half of todo 450 was retired rather than built, and the correction is worth keeping.** The todo's sizing question - "the resume id lives in `agent_state_log` and `pruneStateLog` deletes those rows at `LOG_RETENTION`, so the ability to resume a dead crew silently expires after a week" - was already false when it was written. `agents.session_id` landed in 667bd6d / PR #161 on 2026-08-11, five days before the todo was created; `src/hook.ts`'s `reconcileSessionId` writes it on every hook invocation; it is not in `RESUME_FLIP_COLUMNS`; and `pruneStateLog` touches `agent_state_log`, `wake_block_notices` and `agent_messages`, never `agents`. `agent_resume` already ships. The decision to "accept the 7-day window and say it out loud" (todo 450 comment 1321) was therefore not wrong but VACUOUS, and the doctor line it asked for would have been a hive-authored false statement. The lane shipped no such line.

**One guard here is not pinned by a test, deliberately recorded rather than left to be rediscovered.** `janitor()` gates its close count and its roster on `closeAgentRow()`'s return value, so that when two instances probe the same dead socket only the one whose conditional UPDATE actually closed the row may put it in a record. The race window is between the `SELECT` and the `UPDATE` inside one loop iteration, and there is no way to interleave a second writer there from inside this suite. Mutating the gate away leaves the suite green: the "no second obituary" test passes on the `WHERE status = 'running'` clause instead, which is a real property but a different one. Do not read that test as pinning the gate.

**The first-person exclusion was dropped, and not only for the no-migration bound.** The idea was that a teardown record with no hive-authored close matching it is evidence of "not hive's machinery". Distinguishing a janitor close from an `agent_close` close needs a column that does not exist. It is also worth nothing for the only case that writes a record: hive has no `kill-server` path at all, so for a crew-wide teardown the exclusion excludes nothing.

**What one review round and one lead smoke test found in the first cut, kept because the shapes recur.** Seven findings, all acted on, and the two most valuable were structural rather than severe-sounding.

- **A machine-scoped artifact still has a project-scoped reader.** `reportCrewTeardown` read the machine-wide file and reported it unconditionally, so doctor in project A printed project B's worker names, cwds and `agent_resume` commands. The obvious fix - filter the record to this project - was ruled AGAINST, because it would hide that the death was machine-wide, and every recorded death took a second project's lead. The shape that satisfies both: this project's casualties in full, other projects' as a bare count. `project_id` is written into each member at write time rather than derived by joining the agent rows later, for the reason the restore fix found - a record that cannot be attributed without the store is not a record that survives the store.
- **The moved-on gate was unscoped too, and that half is the more damaging one.** Unscoped, one spawn in a neighbouring project silences the teardown notice permanently. On a machine running two hive projects side by side that is the common case, not the edge. The first bug shows you too much once; this one shows you nothing ever again.
- **`tmuxSaysNothingThere` is true when the tmux BINARY is missing**, so `liveTargets()` answers with an empty snapshot when tmux is simply not on `PATH`, and the first cut turned that into a full teardown record telling a human to go hunt a killer who never existed. This was the highest-priority finding of the seven: it is reachable by an ordinary path AND it reaches the exact dishonesty the prohibitions above were written to prevent, through a different door. The record is gated on `serverAnswered`; the sweep deliberately is not, because that would be a separate behaviour change.
- **`SETTLE_WINDOW` splits one death across two records.** A worker created inside the 15-second window is skipped by the sweep, so tick N files the older workers and tick N+1 files the late one. Reading only the newest record dropped the older crew's session ids, which are the entire point of the file. Fixed at the READING end rather than by merging at write time: merging invents a second write path into the one artifact that has to survive.
- **A guard defeated by the case it was written for.** `isTeardownRecord` checked `Array.isArray(r.crew)` and nothing about the members, while the reader dereferences `m.swept`, `m.agent_id`, `m.name`, `m.cwd` and `m.session_id`. A record with a perfect top level and `crew: [null]` survived it and threw a `TypeError` out of a reporter that is not inside a `check()` wrapper, aborting the rest of doctor. Two independent passes converged here. Both halves shipped - validate every member, AND wrap the reporter - because they defend different things.
- **`socketLastSeenAlive` needed a staleness bound.** A socket path is stable across server restarts, so a sighting of a previous server could label a later server's death `observed`. Very low reachability; acted on anyway because `basis` is the one field the acceptance criteria say must never overclaim. **The 15-second default reads arbitrary and is not: the case it catches is an ordinary laptop sleep.** A long-lived server sights the socket, the machine sleeps for hours, and it wakes to a dead server - without the bound that stale sighting is reported as "hive was watching this socket and saw it alive at the start of that window". That is why a finding that looks like it needs three events inside two 3s ticks was worth acting on. `HIVE_TEARDOWN_SIGHTING_MAX_AGE_MS` exists so the bound can be tested at all, and it is **CLAMPED to the default** so it can only ever shorten. The first cut replaced the bound instead of clamping it, and the lead PROVED the hole rather than arguing it: a sighting, a real 16-second wait, the knob at 600000, and `basis` came back `observed` where the default said `inferred`. The comment above it claimed shortening was safe, which was true and not the whole truth - a knob that can also lengthen needs the clamp, and the clamp makes the claim true by construction rather than by promise.
- **The trim was a non-atomic read-modify-write.** It does not meet this project's act bar - never observed, and the trim only runs at 200 records - and was fixed anyway on cost and failure mode: one line for write-to-temp-then-rename, removing a failure that loses the ENTIRE log to a partial write. Total loss of the only durable trace is the wrong failure mode for the artifact whose whole job is outliving the thing it describes.

**The cap is 200 records**, a backstop against a runaway writer rather than a retention policy: about fifty times this project's whole observed lifetime rate of four crew deaths.

## Reaping a CODEX_HOME (todo 532) is guarded by idempotency, not a conditional-UPDATE claim, and that is a deliberate reading of "concurrency is guarded, not assumed"

`reapCodexHomeForClosedAgent` (`src/spawn.ts`) does not use `closeAgentRow`'s "the conditional UPDATE is the claim" shape, even though both are janitor-sweepable rows. The difference is what the claim is FOR: that pattern earns its keep against an OBSERVABLE side effect. A wake-up claim is atomic because a wake fired twice types into a pane twice - the second firing does something the first already did, visibly, to whatever is on the other end. A `closeAgentRow` race matters for the same reason: the loser must not also file a teardown-record entry for a row the winner already closed.

A reap has no such effect. Two instances racing the same `codex-homes/<key>` directory produce one deleted directory, not two different outcomes: `rmSync(..., { force: true })` ignores `ENOENT` during the recursive walk, not only on the top-level path, so the loser either no-ops on an already-gone entry or throws into its own per-row `catch`. Deleted twice is deleted once - there is no observable difference between "this instance reaped it" and "the other instance already had", so there is nothing for a CAS to arbitrate between.

The actual guard is the write ORDER, not a conditional match: `rmSync` runs before the column clear, never after. A throw from `rmSync` (permissions, a mid-delete race that somehow isn't `ENOENT`) leaves `codex_home` set on the row, so the next `agent_close` call or the janitor's own next tick picks the row up again. The column is the retry token - CLAUDE.md's invariant holds, it is just guarded by idempotency-plus-ordering rather than by the atomic-UPDATE idiom the rest of the janitor uses for state transitions with a visible effect.
